# 0019-I — 가입 신청 시스템 리뉴얼

**버전**: 0019-I  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

현재 가입 신청 시스템은 기본 기능은 동작하지만,
지원자가 단순 목록처럼 누적되어
Guild Chronicle이 추구하는 **‘한 사람과의 만남’**이라는 분위기를 충분히 전달하지 못한다.

0019-I에서는 기존 가입 신청 이벤트 시스템을
기본 가입 신청 시스템으로 승격하여,

모든 지원자가 고유한 배경과 사연을 가진
하나의 가입 신청 이벤트로 등장하도록 구조를 정리한다.

이번 업데이트의 핵심 목표는 다음과 같다.

- 기존 일반 지원 개념 제거
- 모든 지원자에게 가입 신청 이벤트 부여
- 일반 지원 / 특별 지원 UI 구분 제거
- 가입 신청 이벤트 데이터 구조 통합
- 기존 승인·보류·반려·만료 흐름 유지
- 향후 이벤트를 지속적으로 추가할 수 있는 구조 유지

이번 작업에서는 가입 신청 발생 방식 자체는 변경하지 않는다.

---

## 구현 범위

### 1. 가입 신청 이벤트 통합

기존 일반 지원과 특별 지원의 구분을 제거한다.

기존 0019-E의 가입 신청 이벤트 시스템을
모든 지원자가 사용하는 기본 구조로 변경한다.

모든 신규 지원자는 최소 하나의 가입 신청 이벤트를 가진다.

기존처럼 이벤트가 없는 일반 지원자를 생성하지 않는다.

---

### 2. 기본 가입 신청 이벤트

기존 일반 지원자가 사라지므로,
특별한 사건이 없는 평범한 지원자도
하나의 기본 가입 신청 이벤트를 가져야 한다.

예시

- 평범하지만 성실한 신입
- 새로운 삶을 시작하려는 지원자
- 안정적인 소속을 원하는 모험가
- 첫 길드를 찾는 초보 모험가
- 조용히 실력을 증명하고 싶은 지원자

이번 작업에서는 신규 이벤트를 대량 추가하지 않는다.

다만 모든 지원자가 이벤트를 가지도록 하기 위해
필요한 최소 기본 이벤트는 추가할 수 있다.

---

### 3. 기존 이벤트 재사용

0019-E에서 구현된 가입 신청 이벤트를 최대한 재사용한다.

예시

- 형제 함께 지원
- 몰락한 귀족
- 라이벌 길드 출신
- 왕실 추천장
- 은퇴 기사
- 수상한 지원자
- 유명 모험가의 제자
- 고아 출신
- 부상 후 재기
- 빚을 갚기 위한 지원

기존 이벤트 정의와 생성 로직을 불필요하게 다시 만들지 않는다.

---

### 4. 이벤트 데이터 통합

모든 가입 신청 이벤트는
지원자의 이야기를 표현할 수 있는 공통 필드를 가진다.

기본 필드 예시

- 가입 배경
- 현재 상황
- 지원 동기
- 첫인상
- 장점
- 단점

필요한 경우 이벤트별 추가 정보를 가질 수 있다.

예시

- 관련 지원자
- 추천인
- 이전 소속
- 관계 유형
- 동시 지원 그룹
- 특이사항

정확한 필드명은 기존 `RecruitmentEventDefinition` 구조에 맞춰 정리한다.

---

### 5. 기존 필드 정리

기존 이벤트 데이터에

- description
- featureText
- advantageText
- disadvantageText

등 유사 역할의 필드가 있다면
새로운 공통 구조와 중복되지 않도록 정리한다.

기존 데이터를 안전하게 변환하고,
동일한 내용을 여러 필드에 중복 저장하지 않는다.

---

### 6. 지원자 생성 흐름

기존 가입 심사실의 일일 지원자 생성 흐름은 유지한다.

변경 후 흐름

1. 지원자 생성 여부 판정
2. 적용 가능한 가입 신청 이벤트 후보 필터
3. 이벤트 선택
4. 이벤트 조건에 맞는 지원자 생성
5. 이벤트 배경 데이터 연결
6. 기존 가입 심사 대기 목록에 추가

이벤트가 선택되지 않는 상태가 발생하지 않도록
기본 이벤트 fallback을 제공한다.

---

### 7. 이벤트 선택 구조

가입 신청 이벤트는
향후 쉽게 추가할 수 있는 데이터 기반 구조를 유지한다.

새 이벤트 추가 시 가능한 한 다음만 추가하면 되도록 한다.

- 이벤트 정의 데이터
- 필요한 조건
- 필요한 생성 인원
- 필요한 관계 설정

UI와 생성 로직을 매번 별도로 수정하지 않도록 한다.

---

### 8. 이벤트 조건

기존 이벤트 조건을 유지한다.

예시

- 형제 함께 지원: 2명 생성
- 은퇴 기사: 일정 연령 이상
- 유명 모험가의 제자: 특정 직업군
- 고아 출신: 특정 연령 범위
- 부상 후 재기: 성인 지원자
- 몰락한 귀족: 특정 배경

조건을 만족하지 않는 이벤트는 후보에서 제외한다.

---

### 9. 기본 이벤트 fallback

적용 가능한 특별 배경 이벤트가 없거나
이벤트 선택에 실패한 경우에도
일반 지원자를 생성하지 않는다.

대신 기본 가입 신청 이벤트를 적용한다.

예시

```text
평범하지만 성실한 신입
```

모든 지원자는 반드시 이벤트 ID와 이야기 데이터를 가진다.

---

### 10. 일반/특별 구분 제거

다음 표현과 상태를 제거한다.

- 일반 지원
- 특별 지원
- 특별 이벤트 지원자
- 일반 지원자 배지

모든 지원자는 동일한 가입 신청자로 표시한다.

지원자의 차이는

- 이벤트 이름
- 가입 배경
- 현재 상황
- 지원 동기
- 첫인상
- 장점
- 단점

에서 드러나도록 한다.

---

### 11. 가입 신청 목록 UI

가입 신청 목록은
모든 지원자를 동일한 방식으로 표시한다.

표시 정보 예시

- 이름
- 직업
- 종족
- 나이
- 가입 신청 이벤트 제목
- 지원 동기 요약
- 관계 배지 — 필요한 경우

기존 특별 지원 배지는 제거한다.

목록이 지나치게 장황해지지 않도록
이야기 정보는 요약해서 표시한다.

---

### 12. 가입 신청 상세 UI

지원자 상세 화면은
지원자의 이야기 중심으로 구성한다.

표시 정보

- 가입 신청 이벤트 제목
- 가입 배경
- 현재 상황
- 지원 동기
- 첫인상
- 장점
- 단점
- 관련 지원자 — 형제 등 복수 지원 이벤트
- 기존 공개 정보
  - 이름
  - 직업
  - 종족
  - 성별
  - 나이
  - 능력치

기존 잠재력·숨은 특성 비공개 원칙은 유지한다.

---

### 13. 승인·보류·반려 흐름

기존 가입 심사 행동을 그대로 유지한다.

- 승인
- 보류
- 반려
- 보류 해제
- 자동 만료

가입 신청 이벤트 통합을 이유로
새로운 상태나 별도 승인 함수를 만들지 않는다.

---

### 14. 형제 및 복수 지원자

형제 함께 지원 등 복수 지원 이벤트는
기존 그룹 구조를 유지한다.

- 동일 이벤트 그룹 ID
- 관련 지원자 ID
- 관계 표시
- 개별 승인·보류·반려 가능

모든 지원자가 이벤트를 가지게 되더라도
복수 지원 이벤트 그룹이 깨지지 않아야 한다.

---

### 15. 승인 후 정보 보존

지원자가 승인되어 모험가가 된 후에도
가입 당시의 이벤트 출처와 핵심 배경을 보존한다.

보존 예시

- recruitmentEventId
- recruitmentEventTitle
- recruitmentBackgroundSummary
- recruitmentGroupId
- relatedApplicantIds

향후 개인 연대기나 관계 시스템에서 활용할 수 있도록 한다.

이번 작업에서는 후속 스토리를 생성하지 않는다.

---

### 16. 기존 데이터 호환

이미 생성된 지원자 중
가입 신청 이벤트가 없는 데이터가 존재할 수 있다.

이 경우 안전한 기본 이벤트를 적용한다.

예시

- 기존 지원자
- 이벤트 ID 없음
- 기본 가입 신청 이벤트로 보정

기존 지원자 데이터가 깨지거나 사라지지 않아야 한다.

---

### 17. 일일 운영 보고서 연동

신규 지원자 발생 보고는
기존 `recruitment_new_applicants` 흐름을 유지한다.

모든 지원자가 이벤트를 가지므로
보고서에 이벤트 제목 또는 간단한 지원 배경을 포함할 수 있다.

새로운 별도 보고서 시스템은 만들지 않는다.

---

### 18. 연대기 연동

지원자가 승인되면
기존 가입 연대기에 이벤트 배경을 간단히 포함한다.

예시

```text
몰락한 귀족 출신의 지원자가 길드에 합류했다.
```

또는

```text
첫 길드를 찾던 신입 모험가가 길드에 합류했다.
```

장기 개인 스토리나 후속 사건은 구현하지 않는다.

---

### 19. 이벤트 추가 편의성

새로운 가입 신청 이벤트를 추가할 때
다음 파일만 최소 수정하도록 구조를 유지한다.

- 이벤트 정의 데이터
- 필요한 조건 또는 생성 규칙
- 필요한 레이블

UI에서 이벤트별 전용 분기문을 계속 추가하는 구조는 피한다.

---

## 데이터 구조 예시

```ts
interface RecruitmentEventDefinition {
  id: EntityId;
  name: string;
  background: string;
  currentSituation: string;
  motivation: string;
  firstImpression: string;
  advantageText: string;
  disadvantageText: string;
  weight: number;
  applicantCount: number;
  conditions?: RecruitmentEventCondition[];
}
```

위 코드는 예시다.

기존 `RecruitmentEventDefinition`,
`RecruitmentApplicant`,
`Adventurer`,
`EntityId` 구조를 우선 사용한다.

---

## 파일 위치 원칙

현재 프로젝트 구조를 먼저 확인한다.

예시

- 이벤트 타입: 기존 공용 타입 파일
- 이벤트 정의 데이터: 기존 recruitment event 데이터 파일
- 생성·선택 로직: 기존 recruitment simulation
- UI: 기존 recruitment feature
- 레이블: 기존 labels 파일

관련 없는 폴더 구조 개편은 하지 않는다.

구현 전에 관련 공식 문서를 확인하고
필요한 문서를 업데이트한다.

- `docs/00_PROJECT/PROJECT_RULES.md`
- `docs/00_PROJECT/PROJECT_STATUS.md`
- `docs/00_PROJECT/PROJECT_TERMINOLOGY.md`
- `docs/00_PROJECT/ROADMAP.md`
- 가입 심사 관련 SYSTEM 문서

- 가입 신청 이벤트 관련 DATABASE 문서
- 가입 심사 관련 DESIGN 문서

- `docs/02_DATABASE/RECRUITMENT_EVENT_DATABASE.md`

기존 문서를 우선 사용하고
동일 목적의 문서를 중복 생성하지 않는다.

### BRIEFING

관련 BRIEFING이 있다면 업데이트한다.

예시

- `briefings/RECRUITMENT_EVENT_SYSTEM_BRIEFING.md`

BRIEFING에는 다음 철학을 기록한다.

- 모든 지원자는 하나의 사건으로 등장
- 일반/특별 지원 구분 없음
- 지원자의 차이는 배경과 이야기로 표현
- 가입 신청은 명단 생성이 아니라 한 사람과의 만남
- 향후 이벤트는 지속적으로 추가 가능
- 후속 스토리와 관계 연계는 미래 확장

## 구현 원칙

- 기존 가입 심사 기능을 유지한다.
- 기존 가입 신청 이벤트 시스템을 최대한 재사용한다.
- 관련 없는 기능은 수정하지 않는다.
- 구현 범위를 불필요하게 확장하지 않는다.
- 모든 지원자는 반드시 하나의 가입 신청 이벤트를 가진다.
- 일반/특별 구분을 제거한다.
- 이야기 데이터와 실제 능력치 효과를 혼동하지 않는다.
- 지원자 생성 확률과 발생 주기는 변경하지 않는다.
- 기존 승인·보류·반려·만료 흐름을 유지한다.
- 이벤트 추가가 쉬운 데이터 기반 구조를 유지한다.

---

## 금지 사항

- 가입 신청 발생 확률을 변경하지 않는다.
- 가입 심사실 캐파를 변경하지 않는다.
- 일반 지원자 대신 모두 특별한 능력 보너스를 주지 않는다.
- 이야기 장점·단점을 실제 수치 효과로 적용하지 않는다.
- 기존 승인·보류·반려 함수를 교체하지 않는다.
- 지원자의 잠재력과 숨은 특성을 공개하지 않는다.
- 가입 신청 UI 전체를 새 시스템으로 재작성하지 않는다.
- 신규 이벤트를 대량으로 추가하지 않는다.
- 관련 없는 모집·관계·명성 시스템을 수정하지 않는다.
