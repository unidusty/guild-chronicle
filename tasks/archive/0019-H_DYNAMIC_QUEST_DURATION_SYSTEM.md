# 0019-H — 동적 의뢰 기간 시스템 구축

**버전**: 0019-H  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

현재 의뢰는 시작 시 정해진 기간대로만 진행되어,
의뢰 중 발생한 사건과 길드장의 판단이 실제 귀환 일정에 영향을 주지 않는다.

0019-H에서는 의뢰 카드에 표시되는 기간을
확정 기간이 아닌 **최초 예상 기간**으로 취급하고,

진행 중 발생한 실제 사건과 길드장의 선택에 따라

- 실제 수행 기간
- 현재 예상 기간
- 현재 예상 귀환일
- 남은 기간

이 증가하거나 감소하도록 한다.

기간 변화는 단순 무작위가 아니라
실제로 발생한 Quest Event와 길드장의 결정에 근거해야 한다.

이번 작업의 핵심 목표는 다음과 같다.

- 최초 예상 기간과 최초 예상 귀환일 보존
- 현재 예상 기간과 현재 예상 귀환일 갱신
- 이벤트 및 결정 기반 기간 증감
- 동일 사건의 기간 변화 중복 적용 방지
- Adventure Log 및 의뢰 연대기 기록
- 기존 Quest Director와 Mandatory Flow 보존
- 무한 연장 방지
- 향후 의뢰 자동 생성 시스템의 기간 계산 확장 기반 마련

---

## 구현 범위

### 1. 최초 예상 기간

의뢰를 수락하거나 배정할 때
기존 의뢰 기간을 **최초 예상 기간**으로 저장한다.

필요한 정보 예시

- `initialEstimatedDays`
- `initialEstimatedReturnDate`

정확한 필드명은 기존 `Quest`, `QuestProgress`, 날짜 구조에 맞게 정한다.

중요 규칙

- 진행 중 기간이 변경되어도 최초 예상 기간은 변경하지 않는다.
- 최초 예상 귀환일도 변경하지 않는다.
- UI와 연대기에서 최초 계획과 실제 결과를 비교할 수 있어야 한다.

---

### 2. 현재 예상 기간

의뢰 진행 중 사건이 발생하면
현재 예상 기간이 늘어나거나 줄어들 수 있다.

필요한 정보 예시

- `currentEstimatedDays`
- `currentEstimatedReturnDate`
- `durationDeltaDays`
- `durationChanges`

정확한 구조는 기존 상태 관리 방식에 맞게 정한다.

현재 예상 기간은

```text
최초 예상 기간
+
누적 지연 일수
-
누적 단축 일수
```

를 기준으로 계산한다.

같은 정보를 여러 필드에 중복 저장하지 않는다.

---

### 3. 기간 변경 기록

기간 변경은 단순 숫자 수정으로 끝내지 않고
원인과 결과를 기록한다.

필요한 타입 예시

- `QuestDurationChange`
- `QuestDurationChangeReason`
- `QuestDurationChangeSourceType`
- `QuestDurationAdjustmentResult`

기간 변경 기록에는 최소한 다음 정보를 포함한다.

- 변경 기록 ID
- 의뢰 ID
- 발생 날짜
- 원인
- 변경 일수
- 변경 전 예상 기간
- 변경 후 예상 기간
- 변경 전 예상 귀환일
- 변경 후 예상 귀환일
- 관련 이벤트 ID
- 관련 결정 ID
- 진행 단계
- 설명

---

### 4. 기간 증가 원인

다음 사건은 지연 원인이 될 수 있다.

- 산사태로 인한 우회
- 폭우
- 폭설
- 안개
- 길 또는 다리 붕괴
- 흔적 소실
- 보급 부족
- 부상자 이송
- 장비 파손
- 전투 장기화
- 추가 탐사
- 지원 파티 대기
- 안전한 우회 선택

모든 이벤트를 한 번에 연결할 필요는 없다.

현재 Event Pool과 기존 Quest Event 구조를 확인하여
안전하게 연동 가능한 일부 이벤트부터 실제 적용한다.

---

### 5. 기간 감소 원인

다음 사건은 기간 단축 원인이 될 수 있다.

- 지름길 발견
- 현지 안내인 합류
- 정확한 정보 확보
- 목표 조기 발견
- 이동 수단 확보
- 날씨 호전
- 뛰어난 정찰
- 지역 주민의 도움
- 강행군 선택

기간 단축 역시
실제 발생한 이벤트 또는 결정이 있어야만 적용한다.

이벤트가 발생하지 않았는데
임의로 기간만 줄이지 않는다.

---

### 6. 이벤트 연동

기존 Quest Event, Quest Director, Adventure Log와 연동한다.

기간 변화는 다음 중 하나를 근거로 해야 한다.

- Quest Event 발생
- 플레이어 결정
- 지원 파티 도착 대기
- 철수 또는 포기
- 실제 의뢰 단계 변화

기존 EventDefinition에 기간 변화 정보를 직접 추가할지,
별도 매핑 테이블을 둘지는 현재 구조를 검토하여 결정한다.

권장 방향

- 이벤트 정의 또는 공통 매핑에서 기간 변화량을 관리
- UI에서 계산하지 않음
- 동일 이벤트 ID에 대해 한 번만 적용
- eventId 또는 decisionId 기반 중복 방지

---

### 7. 동일 사건 중복 적용 방지

같은 이벤트나 결정으로
기간 변화가 두 번 적용되면 안 된다.

중복 방지 기준 예시

```text
questId + sourceType + sourceId
```

또는

```text
questId + eventId + durationChangeType
```

다음 상황을 반드시 검증한다.

- 동일 Quest Event 재처리
- 같은 결정 버튼 중복 클릭
- React 개발 모드 중복 실행
- 하루 진행 함수 재호출
- 지원 파티 대기 효과 중복 적용

---

### 8. 길드장 판단 연동

일부 사건에서는
길드장의 선택에 따라 기간이 달라질 수 있다.

#### 안전한 우회

- 기간 증가
- 위험 감소

#### 강행 돌파

- 기간 유지 또는 단축
- 위험 증가

#### 현지 지원 요청

- 비용 증가
- 기간 단축 가능

#### 추가 탐사 승인

- 기간 증가
- 추가 성과 가능

#### 즉시 철수

- 목표 포기
- 귀환 일정 재계산

현재 구현 가능한 기존 결정 구조를 우선 재사용한다.

새로운 복잡한 선택 시스템은 만들지 않는다.

---

### 9. 위험도 및 비용 연동 범위

길드장의 판단에 따라
위험도나 비용이 달라질 수 있는 구조를 고려한다.

다만 이번 작업의 핵심은 **기간 변화**다.

따라서 실제 적용 범위는 다음으로 제한한다.

- 기존 위험도 modifier가 있다면 최소 연동 가능
- 기존 Finance 또는 지원 비용 구조가 있으면 최소 연동 가능
- 새로운 비용 시스템은 만들지 않음
- 새로운 위험도 시스템은 만들지 않음

---

### 10. 현재 예상 귀환일

현재 예상 귀환일은
현재 게임 날짜와 남은 예상 기간을 기준으로 계산한다.

프로젝트의 기존 날짜 체계와 `toAbsoluteDay` 또는 관련 날짜 유틸리티를 재사용한다.

필요한 계산 예시

```text
현재 예상 귀환일
=
오늘 날짜
+
현재 남은 예상 일수
```

또는 기존 진행 일수와 총 예상 기간을 기준으로 계산한다.

정확한 방식은 현재 `QuestProgress` 구조에 맞춘다.

날짜 계산을 UI에 중복 작성하지 않는다.

---

### 11. 실제 수행 기간

의뢰가 시작된 날부터 완료 또는 철수한 날까지의
실제 수행 일수를 기록한다.

필요한 정보 예시

- `startedAt`
- `completedAt`
- `actualDurationDays`

의뢰 종료 시

- 최초 예상 기간
- 최종 예상 기간
- 실제 수행 기간
- 총 지연 일수
- 총 단축 일수

를 비교할 수 있어야 한다.

---

### 12. 남은 기간 계산

남은 기간은
현재 예상 기간에서 실제 경과 일수를 제외하여 계산한다.

기간이 변경되면 남은 기간도 즉시 갱신한다.

다음 상태를 허용하지 않는다.

- 현재 예상 기간은 늘었는데 남은 기간은 그대로
- 현재 예상 귀환일과 남은 기간 불일치
- 실제 경과 일수가 총 기간보다 큰데 완료되지 않음
- 기간 단축 후 음수 남은 기간 발생

---

### 13. 진행 단계와 기간 재계산

현재 `calcQuestStage`와 Quest Director가
일수 기반으로 진행 단계를 계산하고 있으므로
기간 변경 시 단계 계산도 일관되게 갱신되어야 한다.

중요 규칙

- 기간 단축으로 Mandatory Step이 사라지지 않음
- 귀환 단계가 비정상적으로 조기 시작되지 않음
- 기간 연장으로 같은 단계가 무한 반복되지 않음
- Quest Director가 변경된 기간을 기준으로 urgency를 재평가
- critical 상태 강제 이벤트 흐름 유지

기존 Quest Director와 Mandatory Flow를 우선 보존한다.

---

### 14. Mandatory Event 보호

기간 단축으로 인해
필수 사건을 수행할 시간이 부족해질 수 있다.

따라서 기간 단축 적용 전
다음 항목을 검증한다.

- 남은 Mandatory Step 수
- 남은 예상 일수
- 현재 진행 단계
- 귀환 진입 가능 시점

필요한 경우 단축량을 제한한다.

예시

```text
요청 단축: -3일
안전하게 가능한 단축: -1일
실제 적용: -1일
```

기간 단축이 Mandatory Flow를 깨뜨리는 경우
단축을 거부하거나 최소 범위로 제한한다.

---

### 15. 무한 연장 방지

기간 연장이 반복되어
의뢰가 끝나지 않는 상황을 방지한다.

다음 규칙을 적용한다.

- 이벤트별 최대 1회 적용
- 의뢰별 총 연장 상한
- 최초 예상 기간 대비 최대 연장 비율 또는 최대 일수
- 귀환 단계에서는 귀환 관련 이벤트만 기간에 영향
- 이미 완료 조건에 도달한 의뢰는 추가 연장하지 않음

예시 방향

```text
최대 연장
=
최초 예상 기간의 50%
또는
최대 +10일
```

정확한 값은 현재 의뢰 길이에 맞게 조정한다.

장거리 의뢰는 별도 상한 확장이 가능하도록 구조를 고려한다.

---

### 16. 기간 단축 하한

기간 단축으로 의뢰가 비정상적으로 즉시 종료되지 않도록 한다.

다음 규칙을 적용한다.

- 최소 전체 기간 보장
- 최소 수행 단계 보장
- 최소 귀환 기간 보장
- Mandatory Step 완료 여유 보장
- 이미 경과한 일수보다 짧게 줄일 수 없음

---

### 17. 귀환 단계 제한

귀환 단계에서는
귀환과 직접 관련된 사건만 기간에 영향을 줄 수 있다.

허용 예시

- 귀환 중 폭우
- 부상자 이송
- 길 붕괴
- 귀환 지름길 발견
- 이동 수단 확보

금지 예시

- 새로운 목표 발견
- 추가 탐사
- 새로운 전투 목표
- 의뢰 목표 조기 발견

기존 귀환 단계 이벤트 제한 규칙과 일치시킨다.

---

### 18. 지원 파티 대기

지원 파티가 도착하기 전
주 파티가 기다리는 선택을 한 경우
기간이 늘어날 수 있다.

기존 `SUPPORT_TRAVEL_DAYS` 구조를 재사용한다.

중요 규칙

- 지원 파티 대기 기간을 매일 반복 누적하지 않음
- 지원 결정 시 한 번만 기간 변화 적용
- 실제 도착 예정일과 현재 예상 귀환일이 일치하도록 계산
- 지원 파티가 도착한 뒤 추가 대기 연장 없음

---

### 19. 철수 및 포기

철수 또는 포기 시
기존 목표 수행 일정은 종료되고
귀환 일정만 재계산한다.

다음 정보를 기록한다.

- 철수 결정 날짜
- 기존 예상 귀환일
- 새 예상 귀환일
- 변경 이유
- 실제 귀환까지 남은 일수

즉시 종료 처리와 귀환 후 보고 구조가 충돌하지 않도록
기존 0019-A 귀환 보고 흐름을 확인한다.

---

### 20. 진행 중 의뢰 UI

진행 중 의뢰 화면에 다음 정보를 표시한다.

- 최초 예상 기간
- 현재 예상 기간
- 최초 예상 귀환일
- 현재 예상 귀환일
- 최초 예상 대비 지연 또는 단축 일수
- 최근 기간 변경 원인
- 현재까지 실제 수행일
- 현재 진행 단계
- 남은 예상 일수

표시 예시

```text
최초 예상 기간: 8일
현재 예상 기간: 10일
현재 예상 귀환: 늦여름 25일
변경: +2일 지연
원인: 산사태로 인한 우회
```

변경이 없는 경우
불필요한 0일 변경 표시를 하지 않는다.

---

### 21. 귀환 보고 UI

0019-A 귀환 보고에
기간 비교 정보를 추가한다.

표시 정보

- 최초 예상 기간
- 최종 예상 기간
- 실제 수행 기간
- 총 지연 일수
- 총 단축 일수
- 주요 기간 변경 원인

기존 정산 흐름은 변경하지 않는다.

---

### 22. Adventure Log 연동

기간 변경이 발생하면
Adventure Log에 기록한다.

기록 내용

- 기간 변경 사건
- 길드장의 선택
- 지연 또는 단축 일수
- 변경된 예상 귀환일
- 현재 진행 단계

필요 시 새로운 Adventure Log category를 추가할 수 있다.

예시

- `delay`
- `schedule_change`

다만 기존 `incident`, `decision`, `return` 범주로 충분하다면
새 범주를 추가하지 않고 기존 구조를 재사용한다.

PROJECT_RULES의
타입·템플릿·CSS·레이블 동시 업데이트 규칙을 준수한다.

---

### 23. Quest Chronicle 연동

의뢰 종료 시
의뢰 연대기에 다음 정보를 보존한다.

- 최초 예상 기간
- 최종 예상 기간
- 실제 수행 기간
- 총 지연 또는 단축 일수
- 주요 기간 변경 원인
- 최초 예상 귀환일
- 실제 귀환일

완료된 의뢰가 state에서 제거되어도
기간 기록은 연대기에 남아야 한다.

---

### 24. 일일 운영 보고서 연동

기간 변경이 발생한 날
기존 일일 운영 보고서에서 확인할 수 있도록 한다.

필요 시 `DailyReportItem` 종류를 추가한다.

예시

- `quest_duration_changed`
- `quest_delayed`
- `quest_shortened`

정확한 식별자는 기존 명명 규칙에 맞게 정한다.

표시 내용

- 의뢰명
- 변경 일수
- 변경 후 예상 귀환일
- 변경 원인

### 25. 의뢰 종류별 기간 확장 준비

향후 의뢰 자동 생성 시스템에서
다음 요소에 따라 최초 예상 기간을 계산할 수 있도록 준비한다.

- 의뢰 종류
- 이동 거리
- 지역 위험도
- 목표 복잡도
- 계절
- 기상
- 권장 인원
- 적 규모

이번 작업에서는 자동 생성 시스템 전체를 구현하지 않는다.

현재는 기존 의뢰의 `totalDays` 또는 동일 필드를
최초 예상 기간으로 안전하게 변환한다.

---

### 26. 의뢰 종류별 권장 기간 문서화

향후 기준으로 다음 범위를 문서에 기록한다.

- 도시 내부 초급 의뢰: 2~4일
- 근교 초급 의뢰: 3~6일
- 일반 지역 의뢰: 5~10일
- 중거리 위험 의뢰: 10~20일
- 장거리 원정: 20~40일 이상
- 대형 원정·레이드: 수십 일~수개월

위 범위는 향후 의뢰 자동 생성 기준이다.

현재 샘플 의뢰의 기간을 전면 재조정하지 않는다.

---

### 27. 호위 의뢰 확장 준비

호위 의뢰는 이동 자체가 수행이므로
일반 의뢰와 다른 기간 구조를 사용할 수 있도록 고려한다.

향후 흐름 예시

```text
출발
→ 이동 중 사건
→ 방어
→ 목적지 도착
→ 길드 귀환
→ 보고
```

이번 작업에서는 호위 전용 기간 시스템을 완성하지 않는다.

기존 호위 의뢰 흐름을 깨뜨리지 않고
향후 별도 계산이 가능한 구조만 준비한다.

---

## 데이터 구조 예시

```ts
interface QuestDurationChange {
  id: EntityId;
  questId: EntityId;
  date: GameDate;
  deltaDays: number;
  reason: string;
  sourceType: "event" | "decision" | "support" | "withdrawal";
  sourceId: EntityId;
  previousEstimatedDays: number;
  nextEstimatedDays: number;
  previousReturnDate: GameDate;
  nextReturnDate: GameDate;
  stage: QuestStage;
}

interface QuestDurationState {
  initialEstimatedDays: number;
  currentEstimatedDays: number;
  startedAt: GameDate;
  initialEstimatedReturnDate: GameDate;
  currentEstimatedReturnDate: GameDate;
  changes: QuestDurationChange[];
}
```

위 코드는 예시이며
기존 `QuestProgress`, `GameDate`, `EntityId` 구조를 우선 사용한다.
