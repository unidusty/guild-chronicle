# 0019-G — 시설 유지비 및 길드 운영비 시스템 구축

**버전**: 0019-G  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

현재 길드는 시설을 보유하고 있지만 시설 유지비와 기본 운영비가 없어,
길드 규모가 커져도 지속적인 운영 부담이 발생하지 않는다.

0019-G에서는 운영 중인 시설에 따른 일일 유지비와
길드 기본 운영비를 도입하여 길드 재정에 지속적인 지출 구조를 추가한다.

핵심 목표는 다음과 같다.

- 운영 중인 시설별 일일 유지비 도입
- 길드 기본 일일 운영비 도입
- `오늘 업무 종료` 과정에서 하루 1회 비용 처리
- 기존 Finance Transaction과 연동
- 일일 운영 보고서에 비용 결과 표시
- 자금 부족 시 경고 및 미납 상태 기록
- 향후 직원 급여, 세금, 시설 수익, 파산 시스템 확장 기반 마련

이번 작업에서는 시설 기능 정지, 철거, 파산 및 게임오버를 구현하지 않는다.

---

## 구현 범위

### 1. 시설 유지비

건설되어 실제로 운영 중인 시설은 일일 유지비를 가진다.

기본 대상

- 길드 홀
- 접수대
- 창고
- 가입 심사실
- 향후 추가되는 길드 시설

시설 정의 데이터에 유지비 정보를 추가한다.

예시

```ts
dailyMaintenanceCost: number;
```

또는 시설 레벨별 유지비 테이블을 사용할 수 있다.

```ts
maintenanceByLevel: {
  1: 20,
  2: 40,
  3: 70,
};
```

정확한 필드명과 구조는 기존 시설 데이터 형식에 맞춘다.

---

### 2. 유지비 발생 대상

다음 시설만 유지비가 발생한다.

- `active`

다음 시설에는 유지비가 발생하지 않는다.

- `unbuilt`
- `constructing`
- `upgrading`

업그레이드 중 시설은 이번 작업에서 운영 중단 상태로 보고 유지비를 부과하지 않는다.

---

### 3. 길드 기본 운영비

시설 유지비와 별도로 하나의 기본 일일 운영비를 적용한다.

기본 운영비는 행정, 공용 소모품, 식량, 청소, 조명, 기타 잡비를
단순화한 비용이다.

이번 작업에서는 세부 항목으로 분리하지 않는다.

예시

```ts
BASE_DAILY_GUILD_OPERATING_COST = 30;
```

정확한 값은 현재 초기 골드와 0019-A~C의 수입 구조를 기준으로 조정한다.

---

### 4. 일일 총 운영비 계산

```text
일일 총 운영비
=
기본 운영비
+
운영 중인 모든 시설의 유지비 합계
```

계산 결과에는 다음 정보가 포함되어야 한다.

- 기본 운영비
- 시설별 유지비
- 시설 유지비 합계
- 당일 총 운영 지출
- 처리 전 길드 자금
- 실제 지불액
- 처리 후 길드 자금
- 미납 금액
- 자금 부족 여부

필요한 타입 예시

- `FacilityMaintenanceEntry`
- `DailyOperatingCostResult`
- `GuildDeficitState`

---

### 5. 처리 시점

시설 유지비와 기본 운영비는
기존 `오늘 업무 종료` 처리에서 하루에 한 번 적용한다.

기존 `processDayEnd` 구조를 먼저 확인한 뒤
시설 공사, 지원자, 의뢰, 세계 이벤트 처리와 충돌하지 않는 위치에 연결한다.

중요 규칙

- 같은 날짜에 비용을 두 번 차감하지 않는다.
- 날짜가 실제로 진행되지 않았다면 추가 비용을 부과하지 않는다.
- 업무 종료 처리 재호출로 중복 거래가 생기지 않아야 한다.

---

### 6. 중복 차감 방지

기존 Finance Transaction의 중복 방지 구조를 우선 재사용한다.

예시

```text
sourceType: daily_operation
sourceId: dateKey
type: facility_maintenance 또는 guild_operating_cost
```

동일한 `(sourceType, sourceId, type)` 거래가 존재하면
같은 날짜에 다시 처리하지 않는다.

다음 상황을 검증한다.

- 업무 종료 버튼 중복 클릭
- 같은 날짜의 `processDayEnd` 재호출
- React 개발 모드 중복 실행
- 향후 저장 복구 후 같은 날짜 재처리

---

### 7. 재정 시스템 연동

기존 0019-B Finance Transaction 시스템을 재사용한다.

추가 거래 종류

- `facility_maintenance`
- `guild_operating_cost`

권장 기록 방식

- 기본 운영비: 하루 1건
- 시설 유지비: 하루 총액 1건
- 시설별 상세: 거래 설명 또는 `DailyOperatingCostResult`에 보존

재정 장부에서 두 비용이 명확히 구분되어야 한다.

---

### 8. 원자 처리

다음 작업은 하나의 처리 흐름으로 완료되어야 한다.

1. 당일 비용 계산
2. 중복 여부 확인
3. 길드 자금 반영
4. Finance Transaction 생성
5. 미납 상태 반영
6. 일일 운영 보고서 결과 생성

다음 상태를 허용하지 않는다.

- 골드는 차감됐지만 거래 기록이 없음
- 거래 기록은 있지만 골드 변화가 없음
- 미납 기록 없이 자금만 0이 됨
- 보고서와 실제 거래 금액이 다름

---

### 9. 자금 부족 처리

길드 자금이 운영비보다 부족해도
시설 철거, 기능 정지, 파산, 게임오버로 처리하지 않는다.

권장 방식

```text
필요 비용: 120G
현재 자금: 70G

실제 지불: 70G
미납: 50G
최종 자금: 0G
```

적용 규칙

- 길드 골드는 0 아래로 내려가지 않는다.
- 지불 가능한 금액까지만 차감한다.
- 부족분은 미납으로 기록한다.
- 자금 부족 경고를 표시한다.

예시 필드

```ts
unpaidOperatingCost: number;
```

또는 기존 구조에 맞는 미납/적자 상태를 사용한다.

---

### 10. 미납 기록

미납 상태에는 최소한 다음 정보를 보존한다.

- 현재 누적 미납액
- 오늘 새로 발생한 미납액
- 발생 날짜
- 발생 원인
- 자금 부족 상태 여부

이번 작업에서는 다음을 구현하지 않는다.

- 미납 자동 상환
- 플레이어 직접 상환
- 미납 이자
- 미납으로 인한 시설 기능 정지

실제 지불액이 0인 경우 기존 Finance 규칙이 0원 거래를 금지한다면,
Finance Transaction 규칙을 깨지 말고 별도 운영비 결과 또는 미납 기록으로 남긴다.

---

### 11. 일일 운영 보고서 연동

기존 `DailyReport`에 운영비 결과를 추가한다.

필요 시 항목 종류를 추가한다.

- `guild_operating_cost`
- `facility_maintenance`
- `operating_cost_unpaid`

보고서 표시 내용

- 기본 운영비
- 시설 유지비 합계
- 당일 총 운영 지출
- 실제 차감액
- 미납액
- 비용 처리 후 길드 자금

자금 부족 시 경고 표시를 적용한다.

---

### 12. 재정 탭 연동

재정 탭에 다음 거래가 구분되어 표시되어야 한다.

```text
- 70G  시설 유지비
- 30G  길드 운영비
```

미납이 있다면 간단한 경고를 표시한다.

```text
운영비 미납: 50G
```

복잡한 부채 관리 페이지는 만들지 않는다.

---

### 13. 길드 홀 연동

길드 홀의 기존 보유 골드 카드 또는 결재 대기 영역을 재사용하여
재정 위험 상태를 표시한다.

예시

- 정상
- 자금 부족
- 운영비 미납

새로운 대형 대시보드 시스템을 만들지 않는다.

---

### 14. 시설 화면 연동

시설 화면에서 각 시설의 현재 일일 유지비를 확인할 수 있도록 한다.

표시 정보

- 시설 레벨
- 현재 일일 유지비
- 필요 시 다음 레벨 유지비

유지비 할인, 효율, 수익 비교는 구현하지 않는다.

---

### 15. 초기 밸런스 원칙

초기 유지비는 다음 방향을 만족해야 한다.

- 하루 이틀 만에 즉시 파산하지 않음
- 시설을 무작정 확장하면 부담 증가
- 의뢰 수수료와 전리품 거래의 필요성 발생
- 초기 길드에서 실제 운영 판단 가능

현재 초기 골드와 실제 의뢰 수수료·전리품 이익을 확인하여 값을 정한다.

---

## 데이터 구조 예시

```ts
interface FacilityMaintenanceEntry {
  facilityId: EntityId;
  facilityName: string;
  level: number;
  cost: number;
}

interface DailyOperatingCostResult {
  date: GameDate;
  baseOperatingCost: number;
  facilityMaintenanceEntries: FacilityMaintenanceEntry[];
  facilityMaintenanceTotal: number;
  totalCost: number;
  paidAmount: number;
  unpaidAmount: number;
  balanceBefore: number;
  balanceAfter: number;
}
```

위 코드는 예시이며 기존 타입과 상태 구조를 우선한다.

## 금지 사항

- 시설 유지비를 UI에서 직접 계산하지 않는다.
- 시설별 유지비를 여러 파일에 중복 하드코딩하지 않는다.
- 동일 날짜에 비용을 두 번 차감하지 않는다.
- 길드 골드를 음수로 만들지 않는다.
- 자금 부족으로 시설을 자동 철거하거나 정지하지 않는다.
- 자금 부족으로 게임오버를 발생시키지 않는다.
- 기존 시설 건설·업그레이드 흐름을 대규모로 변경하지 않는다.
- 기존 Finance Transaction 기록을 초기화하지 않는다.
- 관련 없는 길드 홀 UI 전체를 개편하지 않는다.

## 검증 시나리오

### 시나리오 1 — 정상 차감

1. 운영 중인 시설 존재
2. 오늘 업무 종료
3. 기본 운영비 및 시설 유지비 계산
4. 총액만큼 길드 골드 차감
5. Finance Transaction 생성
6. 일일 운영 보고서 표시

### 시나리오 2 — 비운영 시설

- `unbuilt`, `constructing`, `upgrading` 시설은 유지비 미발생

### 시나리오 3 — 시설 레벨 증가

1. Lv1 유지비 확인
2. 업그레이드 완료
3. 다음 업무 종료부터 Lv2 유지비 적용

### 시나리오 4 — 중복 차감 방지

1. 같은 날짜 처리 재호출
2. 운영비 중복 차감 없음
3. Finance Transaction 중복 생성 없음

### 시나리오 5 — 자금 부족

1. 총 운영비가 현재 자금보다 큼
2. 가능한 금액까지만 차감
