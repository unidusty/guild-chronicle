# 0019-B — 길드 재정 및 회계 시스템 기반 구축

**버전**: 0019-B  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

0019-B에서는 길드의 모든 골드 흐름을 기록하고 관리하는
**재정(Finance) 및 회계(Accounting) 시스템의 기반**을 구축한다.

0019-A에서 구현된 귀환 보고 및 정산 시스템의 결과가
실제 길드 회계 장부에 반영되도록 연결한다.

이번 업데이트의 핵심 목표는 다음과 같다.

- 길드 자금의 증가와 감소를 모두 거래 단위로 기록
- 거래 발생 원인과 결과를 추적 가능하게 구성
- 현재 길드 자금과 회계 장부가 항상 일치하도록 유지
- 향후 유지비, 운영비, 시설 수익, 세계 이벤트 비용을 확장할 수 있는 기반 마련

---

## 구현 범위

### 1. 재정 거래 기록 시스템

길드 자금이 변하는 모든 상황은
반드시 **재정 거래(Finance Transaction)** 로 기록한다.

기본 연동 대상

#### 수입

- 의뢰 중개 수수료
- 창고 전리품 판매

#### 지출

- 전리품 매입
- 시설 건설
- 시설 업그레이드

길드 골드를 직접 증가·감소시키는 코드가 있다면,
이번 작업 범위에 포함되는 흐름은 반드시 재정 거래 생성 함수 또는 공통 재정 처리 함수를 거치도록 한다.

---

### 2. 재정 거래 데이터

각 거래는 최소한 다음 정보를 보존한다.

- 거래 ID
- 게임 날짜
- 거래 종류
- 수입 또는 지출 구분
- 거래 금액
- 거래 전 잔액
- 거래 후 잔액
- 거래 설명
- 관련 시스템 또는 출처
- 관련 엔티티 ID
- 생성 순서 또는 정렬 기준

관련 엔티티 예시

- questId
- returnReportId
- settlementId
- lootItemId
- facilityId
- saleTransactionId

모든 거래가 모든 엔티티 ID를 가질 필요는 없다.
거래 원인에 맞는 ID만 선택적으로 저장한다.

---

### 3. 거래 종류

거래 종류는 향후 확장 가능한 구조로 설계한다.

기본 구현 대상

#### 수입

- `quest_commission`
  - 의뢰 중개 수수료

- `warehouse_sale`
  - 길드 창고 판매 수익

#### 지출

- `loot_purchase`
  - 수행 파티 전리품 매입

- `facility_construction`
  - 시설 신규 건설 비용

- `facility_upgrade`
  - 시설 업그레이드 비용

향후 추가 예정 항목은 타입 확장을 고려하되,
이번 작업에서는 실제 기능을 구현하지 않는다.

- 시설 유지비
- 일일 운영비
- 세계 이벤트 비용
- 지원 파견 비용
- 숙박 수익
- 식사 수익
- 펍 수익
- 제작 비용
- 제작 수익
- 상인 거래
- 벌금 및 위약금

---

### 4. 재정 처리 공통 함수

길드 자금을 변경하고 거래를 기록하는 공통 함수를 구현한다.

예시 역할

- 수입 처리
- 지출 처리
- 잔액 검증
- 거래 레코드 생성
- 거래 전·후 잔액 기록
- 유효하지 않은 금액 차단
- 자금 부족 지출 차단

예시 함수명은 현재 코드 구조에 맞게 정한다.

- `recordFinanceIncome`
- `recordFinanceExpense`
- `applyFinanceTransaction`
- `createFinanceTransaction`

정확한 이름보다 중요한 것은
**자금 변경과 거래 기록이 하나의 처리 흐름에서 동시에 완료되는 것**이다.

---

### 5. 원자성 규칙

한 번의 재정 처리에서는 다음 작업이 분리되어서는 안 된다.

1. 거래 가능 여부 확인
2. 길드 자금 변경
3. FinanceTransaction 생성
4. 관련 시스템 결과 반영

중간 단계만 반영된 상태가 남아서는 안 된다.

예시

- 골드는 차감됐지만 거래가 기록되지 않는 상태 금지
- 거래는 생성됐지만 골드가 변경되지 않는 상태 금지
- 전리품은 창고로 이동했지만 매입 비용이 차감되지 않는 상태 금지
- 시설 건설은 시작됐지만 비용 거래가 없는 상태 금지

---

### 6. 중복 거래 방지

동일한 정산이나 판매, 시설 작업으로 인해
같은 거래가 두 번 생성되지 않도록 방지한다.

필요한 경우 거래에 다음과 같은 출처 정보를 저장한다.

- `sourceType`
- `sourceId`

또는 이에 준하는 구조를 사용한다.

동일한 `sourceType + sourceId + transactionType` 조합이
중복 생성되지 않도록 검증한다.

특히 다음 상황을 확인한다.

- 정산 완료 버튼 중복 클릭
- 창고 판매 처리 중복 호출
- 시설 건설 또는 업그레이드 처리 재호출
- React 개발 모드에서 의도치 않은 중복 실행

---

### 7. 금액 검증

다음 규칙을 적용한다.

- 거래 금액은 0보다 큰 정수만 허용
- 음수 금액을 입력하여 수입과 지출을 뒤집는 방식 금지
- 지출 후 잔액이 0보다 작아지는 거래 금지
- 수입·지출 방향은 거래 종류 또는 명시적 필드로 구분
- 소수점 골드는 사용하지 않음
- 잘못된 거래는 GameState를 변경하지 않음

---

### 8. 재정 장부

길드는 모든 거래 내역을 재정 장부에서 확인할 수 있다.

표시 정보

- 날짜
- 거래 종류
- 수입/지출 구분
- 금액
- 거래 설명
- 거래 후 잔액

선택적으로 표시 가능한 정보

- 관련 의뢰
- 관련 시설
- 관련 전리품
- 관련 정산

정렬 기준

- 최신 거래가 위
- 같은 날짜의 거래는 생성 순서가 늦은 거래가 위

---

### 9. 0019-A 귀환 정산 연동

0019-A의 귀환 보고 정산 완료 시
재정 거래를 자동 생성한다.

#### 의뢰 중개 수수료

- 거래 종류: `quest_commission`
- 방향: 수입
- 금액: 최종 길드 수수료
- 관련 정보: questId, returnReportId 또는 settlementId

#### 전리품 매입

- 거래 종류: `loot_purchase`
- 방향: 지출
- 금액: 길드가 실제로 지급한 총 매입 금액
- 관련 정보: returnReportId 또는 settlementId

전리품을 여러 개 매입한 경우,
현재 구조에 따라 다음 중 하나를 선택할 수 있다.

- 정산 1건당 총액 거래 1건
- 전리품 항목별 거래 여러 건

이번 작업에서는 구현 복잡도를 줄이기 위해
**정산 1건당 총 매입액 거래 1건**을 우선 권장한다.

다만 전리품별 상세 내역은 정산 데이터에서 확인 가능해야 한다.

---

### 10. 창고 판매 연동

길드 창고에서 전리품을 판매하면
재정 거래를 생성한다.

처리 흐름

1. 판매 가능 수량 확인
2. 판매 금액 계산
3. 창고 수량 감소
4. 길드 자금 증가
5. `warehouse_sale` 거래 생성
6. 기존 판매 기록과 연동

기존 `saleTransactions`가 있다면 삭제하거나 대체하지 않는다.

`FinanceTransaction`은 길드 자금 흐름을 기록하고,
기존 `saleTransactions`는 무엇을 판매했는지 기록하는 용도로 역할을 구분한다.

두 기록은 필요 시 `saleTransactionId`로 연결한다.

---

### 11. 시설 비용 연동

시설 건설 및 업그레이드 비용은
재정 지출 거래로 기록한다.

#### 시설 건설

- 거래 종류: `facility_construction`
- 관련 정보: facilityId

#### 시설 업그레이드

- 거래 종류: `facility_upgrade`
- 관련 정보: facilityId

처리 흐름

1. 시설 상태와 비용 검증
2. 길드 자금 충분 여부 확인
3. 자금 차감
4. 재정 거래 생성
5. 건설 또는 업그레이드 시작

자금 차감과 거래 생성이 성공한 경우에만
시설 상태를 변경한다.

---

### 12. Finance Summary

재정 화면 표시를 위해 계산용 요약 데이터를 제공한다.

필요한 정보

- 현재 길드 자금
- 오늘 수입
- 오늘 지출
- 오늘 순변동
- 전체 누적 수입
- 전체 누적 지출
- 최근 거래 목록

요약값은 가능한 한 거래 기록에서 계산한다.

원본 GameState에 동일한 합계 값을 불필요하게 중복 저장하지 않는다.

현재 길드 자금은 기존 Guild 또는 GameState의 골드 값을
단일 진실 공급원으로 유지한다.

## 데이터 구조

필요한 타입을 추가한다.

예시

- `FinanceTransaction`
- `FinanceTransactionType`
- `FinanceTransactionDirection`
- `FinanceTransactionSourceType`
- `FinanceSummary`
- `FinanceDailySummary`

예시 구조는 현재 프로젝트 타입 규칙에 맞게 조정한다.

```ts
type FinanceTransactionDirection = "income" | "expense";

type FinanceTransactionType =
  | "quest_commission"
  | "warehouse_sale"
  | "loot_purchase"
  | "facility_construction"
  | "facility_upgrade";

interface FinanceTransaction {
  id: EntityId;
  date: GameDate;
  type: FinanceTransactionType;
  direction: FinanceTransactionDirection;
  amount: number;
  balanceBefore: number;
  balanceAfter: number;
  description: string;
  sourceType?: string;
  sourceId?: EntityId;
}
```

위 코드는 구조 예시이며,
기존 타입·날짜·ID 체계를 우선 사용한다.

GameState에는 재정 거래 기록 컬렉션을 추가한다.

예시

```ts
financeTransactions: FinanceTransaction[];
```

기존 데이터 구조가 Record 기반이 더 적합하다면
현재 프로젝트 원칙에 맞게 선택한다.

## 금지 사항

- 이번 작업 범위를 벗어난 기능 구현 금지
- 관련 없는 리팩토링 금지
- 기존 거래·판매 기록 임의 삭제 금지

- 같은 거래의 중복 생성 금지
- Adventure Log 및 Quest Director 구조 변경 금지
- 새로운 아이디어의 임의 구현 금지

필요한 추가 아이디어가 있다면
구현하지 말고 완료 보고의 제안 사항으로만 남긴다.
