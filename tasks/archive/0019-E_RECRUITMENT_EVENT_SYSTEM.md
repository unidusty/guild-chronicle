# 0019-E — 가입 신청 이벤트 시스템 구축

**버전**: 0019-E  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

현재 가입 심사 시스템은 지원자가 개별적으로 단순 생성되는 구조다.

0019-E에서는 지원자가 일정 확률로
특별한 배경이나 상황을 가진 상태로 가입을 신청하도록 하여
모험가 모집 과정에 간단한 이야기와 선택의 재미를 추가한다.

이번 업데이트의 핵심 목표는 다음과 같다.

- 특별 가입 신청 이벤트 데이터 구조 구축
- 기존 지원자 생성 시스템과 자연스럽게 연동
- 지원자의 배경 설명, 특징, 장점, 단점을 표시
- 일부 이벤트에서 복수 지원자 생성 지원
- 기존 승인·보류·반려 흐름 유지
- 향후 명성, 충성도, 숨은 특성, 세계 이벤트 연계를 위한 확장 기반 마련

이번 작업에서는 이벤트의 **설명과 기본 생성 구조**까지만 구현한다.

---

## 구현 범위

### 1. 가입 신청 이벤트 데이터 구조

가입 신청 이벤트 정의와
이벤트가 적용된 실제 지원자를 구분한다.

필요한 타입 예시

- `RecruitmentEventDefinition`
- `RecruitmentEventType`
- `RecruitmentEventContext`
- `RecruitmentEventApplicantLink`
- `RecruitmentEventGroup`

정확한 타입명은 기존 가입 심사 및 데이터 구조에 맞게 정한다.

가입 신청 이벤트 정의에는 최소한 다음 정보를 포함할 수 있어야 한다.

- 이벤트 ID
- 이벤트 이름
- 배경 설명
- 특징
- 장점
- 단점
- 기본 발생 가중치 또는 확률
- 생성 인원 수
- 지원자 간 관계
- 직업·종족·성별·나이 등의 제한 조건
- 이벤트 전용 표시 문구
- 중복 허용 여부

---

### 2. 기본 이벤트 목록

초기 구현 대상은 다음과 같다.

- 형제 함께 지원
- 몰락한 귀족
- 라이벌 길드 출신
- 왕실 추천장
- 은퇴 기사
- 수상한 지원자
- 유명 모험가의 제자
- 고아 출신
- 부상 후 재기
- 빚을 갚기 위한 지원

이벤트 정의는 한 곳에서 데이터 기반으로 관리한다.

이벤트별 설명과 조건을
UI와 생성 로직 여러 곳에 중복 작성하지 않는다.

---

### 3. 특별 지원자 발생 방식

기존 `generateDailyApplicants` 또는 동일한 역할의 생성 흐름을 재사용한다.

지원자 생성 시

1. 일반 지원자 생성 여부 판정
2. 특별 가입 신청 이벤트 적용 여부 판정
3. 적용 가능한 이벤트 후보 필터
4. 이벤트 선택
5. 이벤트 규칙에 맞는 지원자 생성
6. 기존 가입 심사 대기 목록에 추가

흐름으로 처리한다.

특별 이벤트가 발생하지 않은 경우
기존 일반 지원자 생성 방식이 그대로 작동해야 한다.

매일 모든 지원자가 특별 이벤트를 갖도록 강제하지 않는다.

---

### 4. 설명 중심 구현 원칙

이번 업데이트에서는 가입 신청 이벤트가
지원자에게 **설명과 간단한 배경 정보**를 제공하는 수준으로 끝낸다.

예시

#### 왕실 추천장

- 왕실 또는 공적 기관의 추천을 받았다는 설명
- 추천장에 대한 특징 표시
- 실제 명성 보너스나 왕실 관계 변화는 없음

#### 몰락한 귀족

- 과거 귀족 가문 출신이라는 설명
- 자존심, 예절, 생활 적응 문제 등의 장단점 텍스트 표시
- 실제 경제·관계·명성 효과는 없음

#### 수상한 지원자

- 출신이나 경력이 불분명하다는 설명
- 의심스러운 첫인상과 위험 요소를 텍스트로 표시
- 숨겨진 전용 직업, 배신 이벤트, 후속 사건은 없음

설명에 적힌 장점과 단점은
이번 작업에서 실제 능력치 보정이나 판정 효과로 연결하지 않는다.

---

### 5. 형제 함께 지원

`형제 함께 지원`은 이번 작업에서 허용하는
대표적인 복수 지원자 이벤트다.

구현 규칙

- 지원자 2명을 함께 생성
- 두 지원자는 동일한 이벤트 그룹 또는 관계 ID로 연결
- 지원자 상세 화면에서 서로 형제 관계임을 확인 가능
- 각각 일반 지원자와 동일하게 승인·보류·반려 가능
- 두 명 모두 반드시 함께 승인해야 하는 강제 조건은 적용하지 않음
- 한 명만 승인하거나 한 명만 반려해도 시스템 오류가 발생하지 않아야 함
- 부분 승인에 대한 특별 반응, 관계 변화, 후속 사건은 구현하지 않음

향후 동시 승인 조건과 부분 승인 반응을 추가할 수 있도록
관계 정보와 이벤트 그룹만 보존한다.

---

### 6. 단일 지원자 이벤트

다음 이벤트는 기본적으로 지원자 1명에게 적용한다.

- 몰락한 귀족
- 라이벌 길드 출신
- 왕실 추천장
- 은퇴 기사
- 수상한 지원자
- 유명 모험가의 제자
- 고아 출신
- 부상 후 재기
- 빚을 갚기 위한 지원

각 이벤트는 최소한 다음 정보를 제공한다.

- 배경 설명
- 특징
- 장점 텍스트
- 단점 텍스트

이번 작업에서는 실제 수치 효과를 적용하지 않는다.

---

### 7. 이벤트 조건

이벤트는 정의된 조건을 만족할 때만 발생할 수 있도록 한다.

조건 예시

- 은퇴 기사: 일정 연령 이상
- 고아 출신: 특정 연령 범위
- 유명 모험가의 제자: 특정 직업군
- 형제 함께 지원: 종족 일치, 성씨 또는 관계 규칙
- 몰락한 귀족: 출신 배경 생성 규칙
- 부상 후 재기: 과거 부상 설명을 가질 수 있는 성인 지원자
- 왕실 추천장: 현재는 명성 조건 없이 낮은 확률로 등장 가능

이번 업데이트에서는 필요한 최소 조건만 구현한다.

명성, 세계 이벤트, 세력 관계 등
아직 구현되지 않은 시스템을 조건으로 강제하지 않는다.

---

### 8. 이벤트 중복 방지

다음 규칙을 적용한다.

- 한 지원자에게 여러 가입 신청 이벤트를 동시에 부여하지 않음
- 동일 이벤트 그룹의 지원자가 중복 생성되지 않음
- 형제 이벤트 생성 시 두 지원자가 각각 별도 일반 이벤트를 추가로 갖지 않음
- 동일한 일일 생성 처리에서 같은 그룹이 두 번 추가되지 않음

---

### 9. 기존 가입 심사 연동

특별 가입 신청 이벤트가 적용된 지원자도
기존 지원자와 동일한 상태 흐름을 사용한다.

- `pending`
- `held`
- `accepted`
- `rejected`
- `expired`

기존 행동도 그대로 유지한다.

- 승인
- 보류
- 반려
- 보류 해제
- 자동 만료

특별 이벤트를 이유로
별도의 심사 상태나 전용 승인 함수를 만들지 않는다.

---

### 10. 지원자 승인 처리

특별 지원자를 승인하면
기존 `acceptApplicant` 또는 동일 역할의 함수를 재사용하여
일반 모험가로 등록한다.

가입 신청 이벤트 정보는
향후 개인 연대기 또는 관계 시스템 확장에 활용할 수 있도록
필요한 최소 출처 정보를 보존한다.

예시

- recruitmentEventId
- recruitmentGroupId
- relatedApplicantIds
- originNote

정확한 저장 위치는 기존 Adventurer 및 연대기 구조를 검토하여 결정한다.

이번 작업에서는 승인 후 전용 후속 이벤트를 발생시키지 않는다.

---

### 11. 지원자 상세 UI

기존 가입 심사 상세 화면에
특별 가입 신청 이벤트 섹션을 추가한다.

표시 정보

- 이벤트 이름
- 배경 설명
- 특징
- 장점
- 단점
- 관련 지원자 이름 — 형제 이벤트 등 복수 지원자일 경우

일반 지원자는 해당 섹션을 표시하지 않는다.

UI는 현재 가입 심사 화면 스타일을 재사용한다.

별도 컷신, 전용 모달, 대화 화면은 만들지 않는다.

---

### 12. 지원자 목록 표시

특별 이벤트 지원자는
목록에서 간단히 구분할 수 있어야 한다.

예시

- `특별 지원`
- 이벤트 이름
- 관계 배지

기존 목록 가독성을 해치지 않는 최소 표시만 추가한다.

---

### 13. 일일 운영 보고서 연동

특별 가입 신청 이벤트가 발생한 경우
기존 신규 지원자 보고 흐름을 재사용한다.

필요 시 보고서 설명에 다음 정보를 추가할 수 있다.

- 특별 지원 이벤트 이름
- 동시 지원 인원
- 관계 정보

새로운 별도 보고서 시스템을 만들지 않는다.

기존 `recruitment_new_applicants` 항목을 우선 확장한다.

---

### 14. 연대기 연동

특별 지원자가 승인되는 경우
기존 가입 연대기 기록에 이벤트 배경을 간단히 포함할 수 있다.

예시

- 왕실 추천장을 지닌 지원자가 길드에 합류
- 몰락한 귀족 출신 지원자가 길드에 합류
- 형제 중 한 명 또는 두 명이 길드에 합류

이번 작업에서는 별도 개인 스토리나 장기 사건을 생성하지 않는다.

## 이벤트별 초기 설명 방향

### 형제 함께 지원

- 두 지원자가 함께 길드에 찾아옴
- 서로를 의지한다는 배경
- 장점: 관계와 배경이 명확함
- 단점: 한 명만 선발할 경우 향후 갈등 가능성
- 실제 갈등 및 관계 효과는 미구현

### 몰락한 귀족

- 몰락한 가문 출신
- 장점: 교육, 예절, 지식에 대한 기대
- 단점: 자존심과 현실 적응 문제
- 실제 능력치·명성 효과는 미구현

### 라이벌 길드 출신

- 타 길드에서 활동했거나 지원한 경력
- 장점: 기존 길드 운영 경험
- 단점: 이력과 이탈 사유에 대한 불안
- 타 길드 관계 효과는 미구현

### 왕실 추천장

- 왕실 또는 공적 기관 추천
- 장점: 신뢰할 만한 추천 배경
- 단점: 추천장의 진위와 정치적 부담 가능성
- 왕실 관계·명성 효과는 미구현

### 은퇴 기사

- 기사단 또는 군 경력을 마친 지원자
- 장점: 경험과 규율
- 단점: 높은 나이 또는 과거 부상
- 전용 직업과 능력 보정은 미구현

### 수상한 지원자

- 출신과 경력이 불명확함
- 장점: 예상 밖의 경험 가능성
- 단점: 신뢰하기 어려움
- 배신·정체 공개 이벤트는 미구현

### 유명 모험가의 제자

- 이름난 모험가에게 배웠다는 배경
- 장점: 훈련 경험에 대한 기대
- 단점: 스승의 명성에 비해 실제 능력은 불확실
- 스승 NPC 및 후속 관계는 미구현

### 고아 출신

- 보호 시설 또는 거리에서 성장
- 장점: 자립심과 생존 경험
- 단점: 교육과 안정적인 관계 경험 부족
- 보호·복지 시스템은 미구현

### 부상 후 재기

- 과거 부상 이후 다시 활동하려는 지원자
- 장점: 의지와 경험
- 단점: 부상 재발 가능성에 대한 우려
- 실제 부상 상태 및 재발 판정은 미구현

### 빚을 갚기 위한 지원

- 개인 또는 가족의 빚 때문에 지원
- 장점: 강한 활동 동기
- 단점: 경제적 압박과 외부 문제 가능성
- 개인 자금·채무 시스템은 미구현

## 데이터 구조 예시

```ts
type RecruitmentEventType =
  | "siblings"
  | "fallen_noble"
  | "rival_guild_origin"
  | "royal_recommendation"
  | "retired_knight"
  | "suspicious_applicant"
  | "famous_adventurer_apprentice"
  | "orphan_background"
  | "injury_comeback"
  | "debt_motivated";

interface RecruitmentEventDefinition {
  id: EntityId;
  type: RecruitmentEventType;
  name: string;
  description: string;
  featureText: string;
  advantageText: string;
  disadvantageText: string;
  weight: number;
  applicantCount: number;
}

interface RecruitmentEventContext {
  eventId: EntityId;
  groupId?: EntityId;
  relatedApplicantIds?: EntityId[];
}
```

위 코드는 예시다.

기존 `RecruitmentApplicant`, `Adventurer`, `EntityId` 구조를 우선 사용한다.

## 파일 위치 원칙

현재 프로젝트 구조를 검토하여 다음 역할을 분리한다.

예시

- 이벤트 타입: 기존 공용 게임 타입 파일
- 이벤트 정의 데이터: `src/data/`
- 생성·선택 로직: `src/game/simulation/recruitment.ts` 또는 관련 파일
- UI: 기존 recruitment feature 내부
- 표시 레이블: 기존 labels 파일

가입 심사 로직이 이미 한 파일에 집중되어 있다면
불필요하게 파일을 과도하게 분리하지 않는다.

관련 없는 폴더 구조 개편은 하지 않는다.

## 향후 예정으로 문서화할 내용

다음 내용은 이번 작업에서 구현하지 않는다.

다만 `ROADMAP.md`, 관련 SYSTEM 문서 또는 BRIEFING의
**향후 확장 / 예정** 항목에 기록한다.

- 길드 명성에 따른 특별 지원자 출현률 변화
- 지역·도시 명성에 따른 지원 배경 변화
- 지원자의 충성도 성향과 가입 이벤트 연계
- 지원자의 숨겨진 특성과 가입 배경 연계
- 세계 이벤트에 따른 특별 지원자 등장
- 기존 모험가의 지인 추천
- 스승과 제자 동시 지원
- 연인 동시 지원
- 라이벌 동시 지원
- 멸망한 길드 생존자 집단 지원
- 은퇴 모험가의 자녀
- 동시 승인 조건
- 부분 승인 시 반응
- 승인·반려에 따른 후속 스토리
- 가입 이벤트 전용 개인 연대기
- 이벤트 연계 의뢰
- 정체 공개 및 재등장 사건
- 장기 개인 스토리 분기

위 항목은 반드시 **미구현 예정 기능**으로 구분한다.

현재 구현 완료 목록에 포함하지 않는다.

ROADMAP의 기존 0020 이후 계획과 충돌하지 않도록
적절한 후속 단계에 배치한다.

## 구현 원칙

- 기존 가입 심사 시스템을 최대한 재사용한다.
- 관련 없는 기능은 수정하지 않는다.
- 구현 범위를 불필요하게 확장하지 않는다.
- 일반 지원자 생성 흐름을 깨뜨리지 않는다.
- 특별 이벤트가 없어도 기존 가입 심사가 정상 작동해야 한다.
- 이벤트 설명과 실제 효과를 혼동하지 않는다.
- 이번 작업의 장점·단점은 설명 텍스트이며 실제 수치 효과가 아니다.
- 복수 지원자는 기존 개별 심사 상태를 그대로 사용한다.
- 향후 확장용 정보는 최소한으로 보존하되 미구현 기능을 미리 구현하지 않는다.
- 새로운 아이디어를 임의로 추가하지 않는다.

---

## 금지 사항

- 새로운 가입 심사 상태를 추가하지 않는다.
- 기존 승인·보류·반려 함수를 대체하지 않는다.
- 지원자의 잠재력과 숨겨진 특성을 공개하지 않는다.
- 가입 이벤트를 이유로 능력치를 강제로 높이거나 낮추지 않는다.
- 왕실 추천장을 이유로 길드 명성을 직접 변경하지 않는다.
- 빚을 갚기 위한 지원자에게 개인 지갑이나 채무 시스템을 추가하지 않는다.
- 수상한 지원자에게 배신 이벤트를 추가하지 않는다.
- 형제 지원자를 무조건 함께 승인하도록 강제하지 않는다.
- 관련 없는 가입 심사 UI 전체 개편을 하지 않는다.
- 작업 범위 밖의 관계·명성·세계 이벤트 시스템을 수정하지 않는다.

## 검증 시나리오

### 시나리오 1 — 일반 지원자

1. 오늘 업무 종료
2. 일반 지원자 생성
3. 특별 이벤트 정보 없음
4. 기존 지원자 목록과 상세 화면 정상 표시
5. 승인·보류·반려 정상 작동

### 시나리오 2 — 단일 특별 지원자

1. 특별 가입 신청 이벤트 발생
2. 지원자 1명 생성
3. 목록에서 특별 지원 표시
4. 상세 화면에서 배경·특징·장점·단점 표시
5. 일반 지원자와 동일하게 승인·보류·반려 가능

### 시나리오 3 — 형제 함께 지원

1. 형제 이벤트 발생
2. 지원자 2명 생성
3. 동일 이벤트 그룹으로 연결
4. 서로의 이름 또는 관계 확인 가능
5. 한 명 승인, 한 명 반려 가능
6. 처리 후 오류나 고아 참조가 발생하지 않음

### 시나리오 4 — 보류 및 만료

1. 특별 지원자를 보류
2. 기존 보류 기간 정상 적용
3. 보류 해제 후 pending 복귀
4. 미처리 시 기존 만료 규칙 정상 적용

### 시나리오 5 — 승인 후 등록

1. 특별 지원자 승인
2. F랭크 모험가로 정상 등록
3. 기존 가입 연대기 생성
4. 이벤트 출처 정보가 필요한 최소 수준으로 보존
5. 능력치·잠재력 공개 규칙 유지

### 시나리오 6 — 중복 방지

1. 동일 일일 생성 처리 재호출
2. 같은 이벤트 그룹이 두 번 생성되지 않음
3. 한 지원자에게 여러 이벤트가 중첩되지 않음

### 시나리오 7 — 기존 시스템 회귀

1. 가입 심사실 비활성 또는 건설 전 상태 확인
2. 기존 잠금 UI 정상 작동
3. 캐파 제한 정상 작동
4. 일반 지원자 생성 확률 정상 작동
5. 일일 보고서 정상 작동
