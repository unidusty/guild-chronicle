# 0019-F — 길드 명성 시스템 구축

**버전**: 0019-F  
**날짜**: 2026-08-03  
**상태**: todo

---

## 목적

현재 길드는 의뢰를 수행하고 성장하지만,
길드의 사회적 평가와 인지도를 나타내는
실제 명성 시스템이 존재하지 않는다.

0019-F에서는 길드의 활동 결과가
**길드 명성(Guild Reputation)** 으로 축적되는 기반을 구축한다.

이번 업데이트의 핵심 목표는 다음과 같다.

- 길드 명성 수치 도입
- 명성 등급 체계 도입
- 의뢰 결과에 따른 기본 명성 변화
- 명성 변화 기록
- 길드 홀에서 현재 명성 확인
- 향후 지역·도시·국가·세력 평판으로 확장 가능한 기반 마련

이번 작업에서는 단일한 **전체 길드 명성**만 구현한다.

---

## 구현 범위

### 1. 길드 명성 수치

길드는 하나의 명성 수치를 가진다.

명성은 길드의 신뢰도, 인지도, 사회적 평가를 의미한다.

기존 `Guild` 또는 길드 상태 구조에
명성 값을 저장할 수 있도록 한다.

예시

```ts
reputation: number;
```

정확한 필드명은 기존 타입과 용어 규칙에 맞게 정한다.

기존 UI에 명성 지표 카드가 이미 존재한다면
더미 값이나 고정 값을 제거하고 실제 명성 데이터를 표시한다.

---

### 2. 명성 기본값

새 게임 또는 초기 GameState에는
명성 기본값을 설정한다.

초기 길드는 아직 알려지지 않은 상태이므로
낮은 명성 구간에서 시작하도록 한다.

정확한 초기 수치는
명성 등급 기준과 함께 설계한다.

기존 저장 데이터 또는 초기 상태 구조에 신규 필드가 없을 경우
안전한 기본값을 적용한다.

현재 저장 및 불러오기 시스템이 아직 구현되지 않았다면
초기 GameState 호환만 보장한다.

---

### 3. 명성 등급

길드 명성은 수치와 함께 등급으로 표현한다.

기본 등급 예시

- 무명 길드
- 신생 길드
- 소규모 길드
- 유명 길드
- 명문 길드
- 전설의 길드

명성 등급은 원본 데이터에 문자열로 중복 저장하지 않는다.

현재 명성 수치를 기준으로
selector 또는 공통 계산 함수에서 등급을 계산한다.

예시 함수

- `getGuildReputationTier`
- `getReputationLabel`
- `calculateReputationTier`

정확한 함수명은 기존 코드 구조에 맞게 정한다.

등급 경계값은 한 곳에서 관리한다.

예시 구조

```ts
const REPUTATION_TIERS = [
  { min: 0, label: "무명 길드" },
  { min: 100, label: "신생 길드" },
  { min: 300, label: "소규모 길드" },
  { min: 700, label: "유명 길드" },
  { min: 1500, label: "명문 길드" },
  { min: 3000, label: "전설의 길드" },
];
```

위 수치는 예시이며,
현재 게임의 보상 규모와 장기 플레이 방향에 맞게 조정할 수 있다.

---

### 4. 명성 변화 기록

명성이 증가하거나 감소할 때마다
변동 내역을 기록한다.

필요한 타입 예시

- `ReputationChange`
- `ReputationChangeType`
- `ReputationSourceType`
- `ReputationSummary`

명성 변화 기록에는 최소한 다음 정보를 포함한다.

- 기록 ID
- 게임 날짜
- 변화량
- 변화 전 명성
- 변화 후 명성
- 변화 원인
- 관련 시스템
- 관련 엔티티 ID
- 설명

관련 엔티티 예시

- questId
- questChronicleId
- worldEventId
- recruitmentEventId

모든 기록이 모든 ID를 가질 필요는 없다.

---

### 5. 명성 변경 공통 함수

명성 수치 변경과 기록 생성을
하나의 공통 함수에서 처리한다.

예시 역할

- 변화량 검증
- 현재 명성 확인
- 명성 증가 또는 감소
- 최소값 처리
- 변화 기록 생성
- 연대기 기록 생성
- 중복 기록 방지

예시 함수명

- `applyReputationChange`
- `recordReputationChange`
- `changeGuildReputation`

정확한 이름보다 중요한 것은
명성 수치 변경과 로그 생성이 분리되지 않는 것이다.

다음 상태를 허용하지 않는다.

- 명성은 변경됐지만 기록이 없는 상태
- 기록은 생성됐지만 명성이 변경되지 않은 상태
- 같은 의뢰 결과가 중복 반영된 상태

---

### 6. 명성 최소값

길드 명성은 음수가 되지 않도록 한다.

명성 감소 결과가 0보다 작아질 경우
최종 명성은 0으로 제한한다.

변화 기록에는 실제 적용된 변화량을 기록한다.

예시

- 현재 명성: 5
- 요청 감소량: -10
- 실제 적용량: -5
- 최종 명성: 0

---

### 7. 의뢰 결과 연동

이번 업데이트에서 실제 명성 변화의 핵심 연동 대상은
기존 의뢰 완료 결과다.

의뢰 결과 등급에 따라
기본 명성 변화량을 적용한다.

권장 방향

- 대성공: 큰 폭 증가
- 성공: 증가
- 간신히 성공: 소폭 증가 또는 변화 없음
- 철수: 소폭 감소 또는 변화 없음
- 실패: 감소
- 대실패: 큰 폭 감소

의뢰 랭크가 높을수록
명성 변화 폭이 커질 수 있도록 설계할 수 있다.

다만 이번 작업에서는
복잡한 공식보다 단순하고 추적 가능한 규칙을 우선한다.

예시

```text
F랭크 성공      +2
D랭크 성공      +5
B랭크 성공      +12
A랭크 대성공    +25
실패            성공 보상의 일부만큼 감소
대실패          더 큰 폭 감소
```

정확한 값은 현재 의뢰 랭크와 장기 플레이 속도에 맞게 조정한다.

---

### 8. 의뢰 정산 시점과 명성 반영 시점

명성 변화는 의뢰 결과가 확정되는 시점에
한 번만 적용해야 한다.

0019-A의 귀환 보고 및 정산 시스템이 존재하므로
다음 중 현재 구조에 가장 자연스러운 한 지점을 선택한다.

권장

- 의뢰 결과 생성 시 명성 변화 예정값 계산
- 실제 명성 반영은 정산 완료 시점에 한 번만 수행

또는 현재 구조상 더 안전하다면

- 의뢰 완료 결과 확정 시 한 번 반영

중요 규칙

- 동일 의뢰에 명성이 두 번 적용되지 않아야 함
- 귀환 보고 생성과 정산 완료에서 중복 반영 금지
- 철수·포기 처리에서 별도 중복 반영 금지
- Quest Chronicle 기록과 실제 명성 기록이 일치해야 함

구현 전 0019-A의 실제 완료 흐름을 먼저 확인한다.

---

### 9. 세계 이벤트 연동

0019-D의 세계 이벤트 시스템이 구현되어 있다면
명성 변화가 필요한 이벤트를 연동할 수 있는 구조만 준비한다.

이번 작업에서는 일부 이벤트에
간단한 명성 변화 효과를 실제 적용해도 된다.

예시

- 왕국 축제 기여: 소폭 증가
- 국경 분쟁 대응 실패: 감소
- 특별한 세계 사건 해결: 증가

다만 플레이어 선택형 세계 이벤트나
복잡한 세력 관계는 구현하지 않는다.

0019-D에 실제 명성 modifier 또는 effect 구조가 없다면
무리하게 세계 이벤트 시스템을 재설계하지 않는다.

---

### 10. 특별 가입 신청 연동

0019-E의 특별 가입 신청 이벤트는
이번 작업에서 기본적으로 명성을 직접 변경하지 않는다.

다만 향후 연동을 위해
명성 조건 또는 명성 영향 필드를 추가할 수 있는 구조를 고려한다.

현재 실제 적용 금지 예시

- 왕실 추천장 지원자 승인 시 명성 증가
- 유명 모험가의 제자 승인 시 명성 증가
- 수상한 지원자 반려 시 명성 증가

위 효과는 이번 작업에서 구현하지 않는다.

---

### 11. 기타 길드 활동

시설 건설, 전리품 판매, 일반 지원자 승인 등
기타 길드 활동은 이번 작업에서 명성 변화에 연결하지 않는다.

명성 변화 원인을 불필요하게 늘리지 않는다.

이번 업데이트의 실제 명성 변화는
의뢰 결과 중심으로 제한한다.

---

### 12. 길드 홀 명성 표시

기존 길드 홀 대시보드의 명성 지표 카드를 재사용한다.

표시 내용

- 현재 명성 수치
- 현재 명성 등급
- 다음 등급까지 필요한 명성
- 필요 시 진행률

현재 UI 스타일을 유지한다.

새로운 대형 페이지를 만들 필요는 없다.

기능 확인이 가능한 간단한 수치와 등급 표시를 우선한다.

---

### 13. 명성 상세 또는 로그 UI

길드 홀 내부에
최근 명성 변동 내역을 확인할 수 있는 최소 UI를 추가한다.

권장 위치

- 명성 지표 카드 클릭 시 간단한 상세 영역
- 길드 홀 대시보드의 최근 명성 변동 목록
- 재정 탭과 유사한 별도 명성 탭

현재 UI 구조를 검토하여 가장 자연스러운 위치를 선택한다.

표시 정보

- 날짜
- 증가 또는 감소
- 변화량
- 변화 원인
- 관련 의뢰 또는 사건
- 변화 후 명성

이번 작업에서는 복잡한 필터, 그래프, 통계는 구현하지 않는다.

---

### 14. 길드 연대기 연동

기존 `ChronicleCategory = "reputation"`을 우선 활용한다.

의미 있는 명성 변화만
길드 연대기에 기록한다.

예시

- 등급이 변경된 경우
- 큰 폭의 명성 증가 또는 감소
- 대성공·대실패로 인한 주요 변화

작은 명성 변화까지 모두 연대기에 남겨
기록이 과도하게 쌓이지 않도록 한다.

세부 변화는 명성 로그에 보존하고,
중요 변화만 연대기에 기록한다.

---

### 15. 등급 변경 기록

명성 변화로 등급이 변경되면
이를 감지하여 별도 알림 또는 연대기 기록을 생성한다.

예시

- 무명 길드 → 신생 길드
- 소규모 길드 → 유명 길드

등급 하락도 가능하도록 한다.

이번 작업에서는 등급 변경으로
추가 보상, 의뢰 해금, 모집 확률 변화 등을 적용하지 않는다.

---

### 16. 일일 운영 보고서 연동

해당 날짜에 명성 변화가 발생한 경우
기존 일일 운영 보고서에서 확인할 수 있도록 한다.

필요 시 `DailyReportItem`에
명성 변화 관련 종류를 추가한다.

예시

- `reputation_changed`
- `reputation_tier_changed`

정확한 식별자는 기존 명명 규칙에 맞게 정한다.

의뢰 정산과 같은 날 명성이 변경된 경우
중복 설명이 과도하게 표시되지 않도록 한다.

---

### 17. 중복 반영 방지

동일한 출처로 같은 명성 변화가 두 번 적용되지 않도록 한다.

필요한 경우 기록에 다음 정보를 저장한다.

- `sourceType`
- `sourceId`
- `changeType`

동일한 조합의 명성 변화가 이미 존재하면
중복 적용하지 않는다.

특히 다음 흐름을 검증한다.

- 정산 완료 버튼 중복 클릭
- 철수·포기 처리 재호출
- 의뢰 완료 함수 재실행
- React 개발 모드의 중복 실행
- 세계 이벤트 처리 재호출

## 기본 명성 변화 방향

### 의뢰 결과

| 결과 | 기본 방향 |
|---|---|
| 대성공 | 큰 폭 증가 |
| 성공 | 증가 |
| 간신히 성공 | 소폭 증가 |
| 철수 | 소폭 감소 또는 변화 없음 |
| 실패 | 감소 |
| 대실패 | 큰 폭 감소 |

### 의뢰 랭크

| 랭크 | 변화 폭 |
|---|---|
| F / E | 작음 |
| D / C | 보통 |
| B / A | 큼 |
| S | 매우 큼 |

실제 수치는 하나의 상수 또는 계산 테이블에서 관리한다.

UI나 정산 코드에서 임의로 값을 작성하지 않는다.

## 데이터 구조 예시

```ts
type ReputationChangeType =
  | "quest_result"
  | "world_event"
  | "recruitment_event"
  | "guild_activity";

type ReputationChangeDirection = "increase" | "decrease";

interface ReputationChange {
  id: EntityId;
  date: GameDate;
  type: ReputationChangeType;
  direction: ReputationChangeDirection;
  amount: number;
  reputationBefore: number;
  reputationAfter: number;
  description: string;
  sourceType?: string;
  sourceId?: EntityId;
}
```

위 코드는 예시다.

기존 `EntityId`, `GameDate`, `Guild`, `GameState` 구조를 우선 사용한다.

GameState에는 명성 변화 기록을 추가한다.

예시

```ts
reputationChanges: ReputationChange[];
```

기존 데이터 구조가 Record 기반이 더 적합하다면
현재 프로젝트 원칙에 맞게 선택한다.

## 파일 위치 원칙

현재 프로젝트 구조에 맞춰 다음 역할을 분리한다.

예시

- 명성 타입: 기존 공용 게임 타입 파일
- 명성 등급 및 변화량 상수: `src/game/constants/` 또는 적절한 데이터 파일
- 명성 계산 및 적용 로직: `src/game/simulation/`
- selector: 기존 selector 구조
- UI: 기존 guildHall feature 내부
- 레이블: 기존 labels 파일

관련 없는 폴더 구조 개편은 하지 않는다.

## 구현 원칙

- 기존 시스템을 최대한 재사용한다.
- 관련 없는 기능은 수정하지 않는다.
- 구현 범위를 불필요하게 확장하지 않는다.
- 명성 수치와 명성 등급 문자열을 중복 저장하지 않는다.
- 명성 변경과 로그 생성을 하나의 처리 흐름으로 관리한다.
- 동일 출처의 명성 변화가 중복 적용되지 않도록 한다.
- 작은 변화는 로그에 기록하고 중요한 변화만 연대기에 기록한다.
- 의뢰 결과 중심의 최소 연동만 실제 구현한다.
- 향후 기능을 미리 구현하지 않는다.
- 새로운 아이디어는 구현하지 않고 완료 보고에서 제안만 한다.

---

## 금지 사항

- 기존 길드 홀 명성 카드를 별도 시스템과 중복 구현하지 않는다.
- 의뢰 결과를 다시 계산하거나 변경하지 않는다.
- Quest Director와 Event Engine을 수정하지 않는다.
- 명성 때문에 의뢰 보상이나 성공률을 변경하지 않는다.
- 명성 때문에 지원자 생성 확률을 변경하지 않는다.
- 명성 때문에 전리품 가격을 변경하지 않는다.
- 명성을 음수로 허용하지 않는다.
- 동일 의뢰에 명성 변화를 두 번 적용하지 않는다.
- 명성 등급을 Guild 원본 데이터에 문자열로 저장하지 않는다.
- 관련 없는 길드 홀 UI 전체 개편을 하지 않는다.

## 검증 시나리오

### 시나리오 1 — 의뢰 성공

1. 의뢰 성공 결과 확정
2. 정해진 시점에 명성 증가
3. 명성 변화 로그 1건 생성
4. 변화 전·후 명성 정확
5. 동일 의뢰 재처리 시 중복 증가 없음

### 시나리오 2 — 의뢰 실패

1. 의뢰 실패 결과 확정
2. 명성 감소
3. 최종 명성이 0 아래로 내려가지 않음
4. 실제 적용된 감소량이 로그에 기록

### 시나리오 3 — 대성공 및 대실패

1. 대성공 시 일반 성공보다 큰 증가
2. 대실패 시 일반 실패보다 큰 감소
3. 의뢰 랭크에 따라 변화 폭 차이 확인

### 시나리오 4 — 등급 상승

1. 명성 변화로 다음 등급 기준 도달
2. 표시 등급 변경
3. 등급 변경 알림 또는 연대기 기록
4. 추가 보상이나 해금은 발생하지 않음

### 시나리오 5 — 등급 하락

1. 명성 감소로 하위 등급 진입
2. 표시 등급 정상 하락
3. 등급 하락 기록 생성

### 시나리오 6 — 길드 홀 표시

1. 현재 명성 수치 표시
2. 현재 등급 표시
3. 다음 등급까지 필요한 수치 표시
4. 명성 로그 최신순 표시

### 시나리오 7 — 기존 시스템 회귀

1. 귀환 보고 생성
2. 정산 완료
3. 재정 거래 정상 처리
4. 전리품 이동 정상 처리
5. 명성 변화 1회만 처리
6. Adventure Log 및 Quest Chronicle 정상 작동
