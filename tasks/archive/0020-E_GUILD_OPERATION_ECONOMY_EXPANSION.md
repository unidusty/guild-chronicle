# 0020-E — 길드 운영 경제 확장

**버전**: 0020-E  
**상태**: todo

---

## 작업 목적

0019-B에서 기본적인 길드 재정 장부와 거래 기록 시스템을 구축했고,
0019-G에서 시설 유지비와 기본 운영비 시스템을 구축했다.

이번 업데이트에서는 길드를 실제로 운영하는 감각을 강화하기 위해
운영 비용과 수익 구조를 확장한다.

이번 작업의 목표는 단순히 골드를 늘리고 줄이는 것이 아니다.

- 길드를 유지하는 데 비용이 든다.
- 시설은 독립적으로 운영된다.
- 직원, 세금, 부채, 시설 수익이 회계에 반영된다.
- 재정 악화는 운영 상태에 영향을 줄 수 있다.
- 모든 경제 활동은 FinanceTransaction에 기록된다.
- 향후 시설, 직원, 시장, 세계 이벤트와 자연스럽게 연결할 수 있다.

이번 작업에서는 각 세부 시스템을 완성하지 않고,
기존 재정 시스템 위에 **길드 운영 경제의 공통 기반**을 구축한다.

---

# 설계 철학

## 1. 길드 경제는 단순한 자동 수입 시스템이 아니다

길드 운영 경제는

- 유지비
- 급여
- 세금
- 부채
- 시설 운영
- 실제 시설 이용
- 운영 정책

이 서로 연결되는 구조로 발전해야 한다.

단순히 하루가 지나면 자동으로 수익이 발생하는 구조를 지양한다.

---

## 2. 시설 수익은 실제 사용이 있을 때 발생한다

시설은 존재만으로 돈을 벌지 않는다.

수익은 시설이 실제로 이용되었을 때 발생해야 한다.

예시

- 여관: 외부 모험가 또는 여행객 숙박
- 펍: 손님 방문
- 식당: 식사 제공
- 치료실: 치료 서비스 제공
- 훈련장: 외부 이용 또는 교육 제공

이번 작업에서는 실제 방문 시스템이 없을 수 있으므로
초기에는 간단한 이용량 또는 이용 이벤트를 생성할 수 있다.

다만 데이터 구조는 반드시 **usage-driven revenue**를 기준으로 설계한다.

---

## 3. 모든 경제 활동은 재정 장부에 남는다

다음 활동은 모두 기존 FinanceTransaction 구조를 사용한다.

- 직원 급여
- 세금
- 시설 운영비
- 시설 수익
- 대출
- 상환
- 이자
- 미납
- 부채 조정

길드 골드를 직접 변경하고 거래 기록을 생략하는 코드를 만들지 않는다.

---

## 4. 시설은 독립적인 손익 구조를 가진다

각 시설은 다음 정보를 개별적으로 가질 수 있어야 한다.

- 운영 비용
- 수익 종류
- 이용 건수
- 수익 금액
- 운영 상태
- 미납 상태
- 운영 정책
- 손익 결과

전체 길드 수익과 별도로
시설별 손익을 계산할 수 있는 구조를 준비한다.

# 구현 범위

## 1. 운영 경제 공통 구조

다음 개념을 공통 데이터 구조로 정리한다.

- 직원 급여
- 세금
- 대출
- 부채
- 상환
- 이자
- 시설 운영비
- 시설 수익
- 시설 이용 기록
- 재정 악화 상태
- 시설 운영 상태

필요한 타입 예시

- `GuildOperatingEconomyState`
- `PayrollEntry`
- `TaxObligation`
- `GuildLoan`
- `DebtPayment`

정확한 타입명은 기존 프로젝트 구조에 맞게 정한다.

---

## 2. 직원 급여 기반

현재 정식 직원 시스템이 없다면
직원 고용·배치 UI를 새로 만들지 않는다.

대신 다음 기반만 구현한다.

- 직원 역할 정의
- 급여 주기
- 급여 금액
- 급여 지급 상태
- 미지급 상태
- FinanceTransaction 연동

초기 직원 역할 예시

- 접수 직원
- 창고 관리자
- 회계 담당
- 기타 운영 직원

직원이 실제로 존재하지 않는 시설에는
급여가 발생하지 않도록 한다.

현재 직원 데이터가 없다면

- 샘플 기본 직원 구조
- 시설별 기본 운영 인력 슬롯
- 또는 운영 직원 placeholder

중 하나를 선택할 수 있다.

다만 신규 직원 고용 시스템은 구현하지 않는다.

---

## 3. 급여 주기

급여는 매일이 아니라 일정 주기로 지급할 수 있도록 한다.

예시

- 7일마다 지급
- 30일마다 지급
- 월말 지급

현재 날짜 체계와 `toAbsoluteDay` 또는 관련 날짜 유틸리티를 재사용한다.

정확한 초기 주기는 현재 게임 속도에 맞게 결정한다.

급여 지급일이 아닌 날에는 거래를 생성하지 않는다.

---

## 4. 급여 처리

급여 지급 시 다음 흐름을 따른다.

1. 지급 대상 직원 확인
2. 총 급여 계산
3. 지급 가능 금액 확인
4. FinanceTransaction 생성
5. 길드 자금 반영
6. 미지급 금액 기록
7. 일일 보고서 반영

급여 거래 종류 예시

```text
staff_salary
```

직원별 개별 거래 또는 하루 총액 거래 중
현재 장부 구조에 적합한 방식을 선택한다.

권장

- 급여 지급 총액 1건
- 직원별 상세 내역은 Payroll 결과 데이터에 보존

---

## 5. 급여 미지급

자금 부족 시 직원 급여를 전액 지급하지 못할 수 있다.

이번 작업에서는 다음만 구현한다.

- 지급 가능 금액
- 미지급 급여
- 미지급 상태
- 경고
- 재정 장부 기록

이번 작업에서 구현하지 않는다.

- 직원 퇴사
- 직원 불만
- 파업
- 시설 기능 정지
- 관계 변화

---

## 6. 세금 기반

길드는 일정 주기마다 세금을 납부할 수 있어야 한다.

세금은 향후 다음 요소를 고려할 수 있도록 설계한다.

- 길드 규모
- 명성
- 총 수익
- 시설 수
- 지역
- 국가 정책
- 세계 이벤트

이번 작업에서는 기본 구조만 구현한다.

초기 세금 방식 예시

- 고정 기본세
- 일정 주기
- 단순 길드 규모 보정

복잡한 누진세와 국가 정책은 구현하지 않는다.

---

## 7. 세금 처리

세금 지급 흐름

1. 납부일 확인
2. 세금 계산
3. 지불 가능 금액 확인
4. FinanceTransaction 생성
5. 길드 자금 반영
6. 미납 세금 기록
7. 보고서 반영

거래 종류 예시

```text
guild_tax
```

세금 미납으로 즉시 처벌, 시설 압류, 명성 하락을 발생시키지 않는다.

---

## 8. 대출 및 부채 기반

길드는 필요한 경우 자금을 빌릴 수 있는 구조를 가진다.

기본 정보

- 대출 ID
- 대출 원금
- 현재 남은 원금
- 이자율
- 대출 날짜
- 상환 주기
- 다음 상환일
- 상환 상태
- 채권자 유형
- 연체 금액

이번 작업에서는 최소한의 대출 1건 구조를 지원한다.

복수 대출을 지원할 수 있는 확장성을 유지한다.

---

## 9. 대출 실행

대출 실행 시

- 길드 자금 증가
- FinanceTransaction 생성
- 부채 상태 저장

거래 종류 예시

```text
loan_received
```

대출 실행은 임의 자동 발생이 아니라
개발 검증용 함수 또는 최소 UI를 통해 실행할 수 있다.

복잡한 금융기관 UI는 만들지 않는다.

---

## 10. 대출 상환

상환 시

- 원금 상환
- 이자 지급
- FinanceTransaction 기록
- 잔여 원금 갱신
- 상환 완료 처리

거래 종류 예시

```text
loan_principal_payment
loan_interest_payment
```

원금과 이자를 구분하여 기록한다.

---

## 11. 연체

상환일에 자금이 부족하면
연체 상태를 기록한다.

이번 작업에서는 다음만 구현한다.

- 연체 금액
- 연체 날짜
- 미납 이자
- 경고
- 재정 장부 기록

이번 작업에서 구현하지 않는다.

- 강제 압류
- 파산
- 명성 하락
- 시설 폐쇄
- 채권자 이벤트

---

## 12. 길드 재정 건강 상태

길드의 재정 상태를 간단히 계산한다.

예시

- `stable`
- `caution`
- `deficit`
- `critical`

판단 요소 예시

- 현재 골드
- 누적 운영비 미납
- 급여 미지급
- 세금 미납
- 대출 잔액
- 당일 순손익

정확한 등급과 기준은 한 곳에서 관리한다.

재정 건강 상태는 원본 데이터에 문자열로 중복 저장하기보다
selector 또는 계산 함수로 도출하는 것을 우선한다.

---

## 13. 운영 상태

재정 악화가 운영에 영향을 줄 수 있는 구조를 준비한다.

상태 예시

- 정상 운영
- 운영비 미납
- 급여 미지급
- 세금 미납
- 부채 부담
- 재정 위기

이번 작업에서는 표시와 기록까지만 구현한다.

실제 시설 기능 제한은 적용하지 않는다.

# 시설 운영

## 14. 시설 운영 상태

시설별로 운영 상태를 가질 수 있도록 한다.

예시

- `open`
- `closed`
- `suspended`
- `understaffed`

현재 시설 시스템의 `active`, `constructing` 등 건설 상태와
운영 상태를 혼동하지 않는다.

시설 상태 예시

```text
건설 상태: active
운영 상태: open
```

이번 작업에서는 운영 상태를 표시하고 수익·비용 계산에 활용한다.

---

## 15. 시설 운영비

0019-G의 시설 유지비와 별도로,
수익 시설은 운영할 때 추가 운영비를 가질 수 있다.

예시

- 식재료
- 연료
- 소모품
- 세탁
- 청소
- 서비스 비용

거래 종류 예시

```text
facility_operating_cost
```

시설 유지비와 운영비를 구분한다.

- 유지비: 시설을 보유하는 비용
- 운영비: 실제 서비스를 제공할 때 발생하는 비용

---

## 16. 초기 수익 시설 구조

향후 수익 시설 예시

- 여관
- 식당
- 펍

현재 프로젝트에 해당 시설이 실제로 존재하지 않는다면

- 시설 정의 구조
- 수익/비용 구조
- 샘플 데이터
- 계산 함수

까지만 준비한다.

이번 작업에서 신규 시설 건설 기능이나 시설 확장 UI를 만들지 않는다.

---

## 17. 시설 이용 기록

시설 수익은 실제 이용 기록에서 발생해야 한다.

필요한 정보 예시

- 이용 기록 ID
- 시설 ID
- 이용 날짜
- 이용 종류
- 이용 인원
- 단가
- 총 수익
- 운영비
- 순수익
- 이용 원인
- 관련 세계 이벤트 또는 방문자

예시 타입

```ts
interface FacilityUsageRecord {
  id: EntityId;
  facilityId: EntityId;
  date: GameDate;
  usageType: FacilityUsageType;
  quantity: number;
  unitRevenue: number;
  grossRevenue: number;
  operatingCost: number;
  netRevenue: number;
  sourceType?: string;
  sourceId?: EntityId;
}
```

---

## 18. 시설 이용 발생

현재 방문 시스템이 없다면
초기에는 단순한 일일 이용 판정을 사용할 수 있다.

예시

- 시설이 open 상태
- 시설이 존재
- 최소 조건 충족
- 이용 이벤트 발생
- 이용 기록 생성
- 수익과 운영비 반영

중요 원칙

- 시설이 존재한다는 이유만으로 자동 고정 수익을 지급하지 않는다.
- 이용 기록 없이 시설 수익을 생성하지 않는다.
- 같은 날짜 같은 이용이 중복 생성되지 않는다.

---

## 19. 시설 수익

시설 이용 기록에 따라 수익이 발생한다.

예시 거래 종류

- `lodging_revenue`
- `meal_revenue`
- `pub_revenue`

수익 처리 흐름

1. 이용 기록 생성
2. 총 수익 계산
3. 운영비 계산
4. 수익 FinanceTransaction 생성
5. 운영비 FinanceTransaction 생성
6. 시설별 손익 계산
7. 일일 보고서 반영

---

## 20. 시설 손익

시설별로 다음 값을 확인할 수 있어야 한다.

- 오늘 이용 건수
- 오늘 총 수익
- 오늘 운영비
- 오늘 순수익
- 최근 누적 수익
- 최근 누적 비용

이번 작업에서는 복잡한 월별 통계와 그래프는 구현하지 않는다.

---

# 시설 운영 정책

## 21. 운영 정책 데이터 구조

향후 시설 운영 정책을 선택할 수 있도록 구조를 준비한다.

이번 작업에서는 UI와 실제 정책 효과를 전부 구현하지 않아도 된다.

예시

### 여관

- 저가 운영
- 일반 운영
- 고급 운영

### 펍

- 조용한 운영
- 일반 운영
- 활기찬 운영

### 식당

- 검소한 식사
- 일반 식사
- 고급 식사

운영 정책 데이터는 다음 영향을 가질 수 있도록 설계한다.

- 이용 단가
- 운영비
- 방문 가능성
- 명성
- 이벤트
- 소문
- 만족도

---

## 22. 정책 기본값

각 수익 시설에는 기본 운영 정책이 있어야 한다.

정책 UI가 없더라도

# FinanceTransaction 확장

## 24. 거래 종류 추가

기존 FinanceTransactionType을 확장한다.

예시

### 지출

- `staff_salary`
- `guild_tax`
- `facility_operating_cost`
- `loan_principal_payment`
- `loan_interest_payment`

### 수입

- `loan_received`
- `lodging_revenue`
- `meal_revenue`
- `pub_revenue`

필요한 경우

- `salary_unpaid`
- `tax_unpaid`
- `loan_overdue`

등은 FinanceTransaction이 아니라 별도 미납 기록으로 처리한다.

type + sourceType + sourceId
