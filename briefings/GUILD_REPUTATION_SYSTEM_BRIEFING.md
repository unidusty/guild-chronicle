# GUILD REPUTATION SYSTEM BRIEFING

## 핵심 철학

명성은 길드가 세상에 남기는 흔적이다.

의뢰 하나가 끝날 때마다
마을 사람들의 입에서 길드의 이름이 오르내리거나, 혹은 잊혀진다.

Guild Chronicle의 명성 시스템은
숫자 하나의 변화보다
그 변화가 어디서 비롯되었는지를 추적하는 것을 목적으로 한다.

---

## 설계 방향

### 단일 수치, 파생 등급

명성은 하나의 정수 수치로만 저장한다.

등급("유명 길드", "명문 길드" 등)은 수치로부터 항상 실시간으로 계산된다.
데이터에 등급 문자열을 중복 저장하지 않는다.

이 원칙은 나중에 도시별·지역별 명성으로 확장될 때도 동일하게 적용된다.

### 변화의 단일 진입점

모든 명성 변화는 `applyReputationChange`를 통해서만 이루어진다.

수치를 직접 조작하거나
명성과 기록을 분리해서 처리하는 코드 경로는 허용하지 않는다.

이 원칙은 중복 적용 방지와 기록 일관성을 보장한다.

### 연대기는 중요한 변화만

작은 명성 변화(±20 미만, 등급 미변경)는 변동 기록에만 남긴다.
연대기에는 등급 변경이나 큰 폭의 변화만 기록한다.

연대기가 사소한 숫자 변동으로 채워지지 않도록 한다.

---

## 현재 구현 범위 (0019-F)

- 단일 전체 길드 명성 수치
- 7등급 명성 체계 (무명 → 전설)
- 의뢰 결과별 명성 변화 (6결과 × 7랭크 테이블)
- 정산 완료 시 명성 적용 (sourceId 기반 중복 방지)
- 명성 변동 기록 (`reputationChanges`)
- 중요 변화 연대기 자동 생성
- 길드 홀 명성 탭 (현재 수치·등급·진행률·등급 기준표·변동 기록)

## 0020-B 확장 — 명성 활용 시스템

명성은 이제 숫자 기록을 넘어 실제 콘텐츠의 조건이 된다.

### 설계 원칙

- 명성은 지원자 능력이나 상점 할인을 주지 않는다
- 명성은 세상이 길드를 바라보는 시선과 새로운 이야기의 범위를 넓히는 기준이다
- 모든 콘텐츠 조건은 데이터만 추가해서 확장한다 — UI 분기 추가 없음

### 추가된 구조

**`ReputationCondition`** — 콘텐츠 게이팅

Quest 등 콘텐츠에 `reputationCondition?: ReputationCondition`으로 붙인다.
`minReputation`/`maxReputation`으로 노출 범위를 지정한다.

**명성 이벤트** — 등급 도달 시 Inbox 알림

등급 상승 시 `REPUTATION_EVENT_DATA`에서 해당 등급의 이벤트를 조회해
`pendingReputationEvents`에 추가한다.
Inbox가 이를 `reputation_event` 타입 항목으로 파생한다.
길드장이 클릭하면 `dismissReputationEvent`로 제거된다.

**의뢰 연동** — 명성 조건 퀘스트

`reputationCondition`이 있는 퀘스트는 조건 미충족 시 게시판에서 숨겨진다.
조건 충족 시 자동으로 표시된다.

**하루 종료 보고** — 당일 명성 변화 요약

`processDayEnd`가 당일 `reputationChanges`를 스캔하여 보고서에 추가한다.

## 향후 확장 방향

### 지역·도시·세력 평판

현재의 단일 명성은 확장의 씨앗이다.

향후에는 다음과 같이 분화될 수 있다.

- 도시별 명성 (퀘스트 수행 지역에 따라 차등)
- 지역별 명성 (수도·변경·항구 등)
- 국가별 명성 (외교·왕실 신뢰)
- 세력별 평판 (귀족·상인 길드·타 길드·지역 주민)

`ReputationChangeType` 유니온에 `"world_event"` 등이 이미 포함되어 있으므로
소스 유형별 명성 분리가 가능한 구조로 설계되어 있다.

### 명성 이벤트 선택지 분기

현재 명성 이벤트는 정보 알림(requiresAction: false)이다.

향후에는 선택지가 붙은 결정 사항으로 확장할 수 있다.

- 귀족 요청 수락/거절 → 보상·관계 변화
- 행사 초청 참여/불참 → 명성 추가 변화
- 협력 제안 수락 → 연계 의뢰 생성

### 명성 소비

명성을 자원으로 소비하는 방향도 고려할 수 있다.

다만 이 방향은 게임의 핵심 경제 균형에 영향을 주므로
별도 설계 검토가 필요하다.
